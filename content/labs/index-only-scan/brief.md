# Задача: довести запрос до Index Only Scan

Дашборд опрашивает витрину каждые пять секунд одним и тем же запросом. Сам по
себе он не медленный — но при такой частоте разница между «читает четыреста
страниц» и «читает пять» это разница в нагрузке на базу.

## Запрос

Менять его нельзя — он зашит в дашборд:

```sql
SELECT status, count(*)
FROM orders
WHERE tenant_id = 42
  AND created_at >= TIMESTAMPTZ '2026-02-01'
  AND created_at <  TIMESTAMPTZ '2026-03-01'
GROUP BY status;
```

## Задача

Добиться, чтобы запрос выполнялся **без единого обращения к таблице**: в плане
`Index Only Scan`, а `Heap Fetches` равен нулю.

## Что считается решённым

1. **В плане `Index Only Scan`** по таблице `orders`.
2. **`Heap Fetches: 0`** — ни одного похода в таблицу за строками.
3. **Результат верен** — совпадает с независимым расчётом.
4. **Данные на месте** — все 300 000 строк.
5. **Индексов не больше трёх.** Насыпать десяток «на всякий случай» — не
   решение: за каждый платит каждая вставка.

## С чего начать

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT status, count(*) FROM orders
WHERE tenant_id = 42
  AND created_at >= TIMESTAMPTZ '2026-02-01'
  AND created_at <  TIMESTAMPTZ '2026-03-01'
GROUP BY status;

-- Какие индексы уже есть и по каким колонкам
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'orders';
```

Два вопроса, на которые надо ответить:

- **Какие колонки нужны запросу целиком?** Не только те, что в фильтре.
- **Почему подходящего индекса бывает мало?** Этот способ доступа пропускает
  таблицу, только если известно, что строки на странице видны всем. Откуда это
  известно и кто обновляет такие сведения — вторая половина задачи.

Причина в каждом варианте своя, и не в каждом дело в самом индексе.

Строка подключения выведена рядом с кнопкой запуска. База пересоздаётся при
каждом запуске лабы.
