# Разбор

Открывается после сдачи.

## Полный набор проверок

```sql
-- 1. Уникальность ключа
INSERT INTO dq_checks (name, query) VALUES (
    'orders_id_unique',
    $q$SELECT order_id, count(*) FROM orders
       GROUP BY order_id HAVING count(*) > 1$q$
);

-- 2. Полнота обязательного поля
INSERT INTO dq_checks (name, query) VALUES (
    'orders_customer_not_null',
    $q$SELECT order_id FROM orders WHERE customer_id IS NULL$q$
);

-- 3. Валидность суммы
INSERT INTO dq_checks (name, query) VALUES (
    'orders_amount_positive',
    $q$SELECT order_id, amount FROM orders WHERE amount <= 0$q$
);

-- 4. Допустимые значения статуса
INSERT INTO dq_checks (name, query) VALUES (
    'orders_status_known',
    $q$SELECT order_id, status FROM orders
       WHERE status NOT IN ('new', 'paid', 'shipped', 'cancelled')$q$
);

-- 5. Ссылочная целостность
INSERT INTO dq_checks (name, query) VALUES (
    'orders_customer_exists',
    $q$SELECT o.order_id FROM orders o
       LEFT JOIN customers c ON c.customer_id = o.customer_id
       WHERE o.customer_id IS NOT NULL AND c.customer_id IS NULL$q$
);

-- 6. Актуальность
INSERT INTO dq_checks (name, query) VALUES (
    'orders_fresh',
    $q$SELECT max(created_at) AS last_order FROM orders
       HAVING max(created_at) < now() - interval '2 days'$q$
);
```

## Почему именно так

**Уникальность через группировку.** `GROUP BY ключ HAVING count(*) > 1` —
канонический вид: он возвращает не только факт нарушения, но и сам ключ, по
которому дальше искать причину. Ограничение уникальности в схеме было бы
надёжнее, но лаба про случай, когда его поставить нельзя: витрина собирается
загрузкой, и падение на вставке остановило бы весь пайплайн.

**`NOT IN` со списком литералов** безопасен, потому что в списке нет `NULL`.
Если бы допустимые значения брались подзапросом, `NOT IN` сломался бы на
первом же `NULL` и проверка тихо перестала бы находить что-либо — тот самый
случай из теории.

**Антисоединение с явным исключением `NULL`.** Без условия
`o.customer_id IS NOT NULL` эта проверка ловила бы заодно и пропуски, то есть
два разных дефекта одной проверкой. Формально это проходит, практически —
плохо: по срабатыванию непонятно, что случилось, и лечение у случаев разное.

**Актуальность через `HAVING`.** Приём, который стоит запомнить: агрегат без
`GROUP BY` возвращает ровно одну строку, а `HAVING` её отфильтровывает. При
норме — ноль строк, при проблеме — одна, с самим значением. Тот же результат
даёт `SELECT ... WHERE (SELECT max(...)) < ...`, но с `HAVING` короче.

## Чего делать не следовало

**Проверка, срабатывающая всегда.** `SELECT 1` поймает все шесть дефектов и не
будет значить ничего. Именно поэтому отсутствие ложных тревог проверяется
первым: пока проверки шумят, их способность что-то ловить не рассматривается
вовсе.

**Одна проверка на всё.** Запрос, объединяющий шесть условий через `OR`,
формально пройдёт. Но при срабатывании он скажет только «что-то не так», а
разбираться придётся вручную. Проверки различают по названиям в том числе
поэтому.

**Слишком широкий порог.** Проверка `amount > -1000000` технически валидна и
бесполезна. Порог должен отражать бизнес-смысл, а не подгоняться под то, чтобы
не срабатывать.

## Как это выглядит в жизни

Тот же реестр в реальном проекте — это либо тесты dbt в YAML рядом с моделью,
либо набор SQL-файлов, которые прогоняет задача оркестратора. Форма разная,
идея одна: **проверка это запрос, возвращающий нарушения, и пустой результат
означает успех**.

Что добавляется в настоящем проекте поверх:

- **Уровень строгости.** Часть проверок останавливает загрузку, часть только
  предупреждает. Решение содержательное: неверные данные хуже устаревших там,
  где считают деньги, и наоборот там, где нужен оперативный дашборд.
- **Сохранение плохих строк.** «Проверка упала, 1523 строки» — загадка. Плохие
  строки складывают в отдельную таблицу, чтобы можно было посмотреть.
- **Адресат.** У каждого срабатывания должен быть конкретный ответственный.
  Оповещение в общий канал не читает никто.

## Что унести с собой

Набор проверок деградирует сам по себе: они начинают срабатывать ложно, их
отключают «на время», данные меняются, а проверки нет. Живут только те, что
лежат в одном репозитории с кодом пайплайна и меняются тем же коммитом.

И главный признак, за которым стоит следить: **проверка, ни разу не
сработавшая за год, подозрительна**. Либо данные идеальны, либо она сравнивает
пустое с пустым — и отличить одно от другого можно только намеренно испортив
данные, ровно как это делает чекер этой лабы.
