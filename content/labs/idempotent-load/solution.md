# Разбор

Открывается после сдачи. Если читаешь до — задача перестанет чему-либо учить.

## Общий подход

Первый шаг во всех вариантах одинаков — прочитать процедуру:

```sql
\sf load_day
```

Второй — воспроизвести инцидент:

```sql
TRUNCATE orders_daily;
CALL load_day(DATE '2026-03-11');
SELECT * FROM orders_daily WHERE day = '2026-03-11';
CALL load_day(DATE '2026-03-11');
SELECT * FROM orders_daily WHERE day = '2026-03-11';
```

Дальше вопрос ровно один: **что процедура делает с уже существующей строкой за
этот день?** Вариантов три — не замечает, удаляет не ту, пропускает вставку, —
и каждый соответствует одному варианту лабы.

## Вариант 1: вставка без удаления

```sql
INSERT INTO orders_daily (day, orders, revenue)
SELECT p_day, count(*), sum(amount) FROM raw_orders WHERE created_at = p_day;
```

Каждый вызов добавляет строку. После двух вызовов в витрине два кортежа за
один день, и любой отчёт, суммирующий выручку, удваивает её.

**Решение — delete-insert в одной транзакции:**

```sql
CREATE OR REPLACE PROCEDURE load_day(p_day date)
LANGUAGE plpgsql AS $$
BEGIN
    DELETE FROM orders_daily WHERE day = p_day;

    INSERT INTO orders_daily (day, orders, revenue)
    SELECT p_day, count(*), coalesce(sum(amount), 0)
    FROM raw_orders
    WHERE created_at = p_day;
END;
$$;
```

Тело процедуры выполняется в транзакции вызова, поэтому промежуточное
состояние «строки удалены, новые не вставлены» снаружи не видно. Это
существенно: без транзакции падение между операциями оставило бы витрину без
дня — то есть хуже, чем задвоение, потому что заметно позже.

## Вариант 2: удаляется не тот день

```sql
DELETE FROM orders_daily WHERE day = current_date;   -- ← вот здесь
```

Автор знал про delete-insert. Но границу взял из `current_date`, а не из
параметра. Пока загрузка идёт день в день, всё сходится; ломается она на
повторе за прошлое число и на backfill — ровно там, где идемпотентность и
нужна.

Хуже того, вызов за 3 марта удаляет строку за **сегодня**, то есть портит день,
к которому не имеет отношения.

**Решение — брать день из параметра:**

```sql
DELETE FROM orders_daily WHERE day = p_day;
```

Это тот же принцип, что и в оркестрации: границы обрабатываемого периода
берутся из контекста прогона, а не из текущего времени. Формулировка
универсальна — она одинаково верна для Airflow, dbt и SQL-процедуры.

## Вариант 3: идемпотентно и бесполезно

```sql
INSERT INTO orders_daily (...)
SELECT ...
ON CONFLICT (day) DO NOTHING;
```

Задвоения нет: есть уникальный индекс по дню, повтор ничего не меняет.
Формально процедура идемпотентна.

И при этом неверна. Источник дописывает строки задним числом — заказ за 3
марта может приехать 5-го. Строка за 3 марта в витрине уже есть, значит вставка
пропускается, и опоздавший заказ не попадёт туда **никогда**. Витрина тихо
расходится с источником и остаётся такой навсегда.

**Решение — обновлять, а не пропускать:**

```sql
INSERT INTO orders_daily (day, orders, revenue)
SELECT p_day, count(*), coalesce(sum(amount), 0)
FROM raw_orders
WHERE created_at = p_day
ON CONFLICT (day) DO UPDATE
SET orders = excluded.orders, revenue = excluded.revenue;
```

`excluded` — это строка, которую пытались вставить. Delete-insert здесь тоже
годится и даёт тот же результат.

**Что унести из этого варианта:** идемпотентность — не цель, а свойство. Цель
в том, чтобы витрина соответствовала источнику после любого числа запусков в
любом порядке. Процедура, которая при повторе не делает ничего, удовлетворяет
определению идемпотентности и не удовлетворяет цели.

## Чего делать не следовало

**Удалять всю витрину.** `DELETE FROM orders_daily` без условия делает
процедуру идемпотентной: сколько ни вызывай за один день, результат один. Но
загрузка одного дня стирает все остальные — и оркестратор, грузящий дни по
одному, оставит в витрине последний. Отдельная проверка `neighbours_untouched`
стоит именно ради этого случая.

**Менять сигнатуру.** Процедуру вызывает оркестратор, и он про правки не
знает. Изменение сигнатуры означает, что чинит один человек, а ломается у
всех.

## Что проверял чекер

1. **Источник не тронут** — все 200 000 строк `raw_orders` на месте.
2. **Повторный вызов ничего не меняет** — снимок витрины до и после совпадает.
3. **Соседние дни не пострадали** — загрузка 11 марта не трогает 10-е и 12-е.
4. **Опоздавшая строка подхватывается** — чекер дописывает запись в источник
   задним числом и вызывает процедуру снова.
5. **Числа совпадают** с независимым расчётом по `raw_orders`.

Чекер не читает текст процедуры. Он вызывает её в сценариях, ради которых лаба
существует, поэтому засчитывается любое верное решение: delete-insert, MERGE,
upsert, подмена секции.

## Что унести с собой

Проверка загрузки на идемпотентность — это один вопрос: **что будет, если
запустить её дважды подряд?** Если ответ «данные задвоятся» — задача
неидемпотентна, и рано или поздно она будет запущена дважды: ретрай,
перезапуск после инцидента, backfill, сбой после записи, но до отметки об
успехе.

И второй вопрос, который забывают: **что будет, если данные в источнике
изменились между запусками?** Идемпотентность без него превращается в
«ничего не делать», а это тоже неправильный ответ.
