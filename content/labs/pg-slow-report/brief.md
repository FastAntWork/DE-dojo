# Инцидент: отчёт по событиям тормозит

**23:40.** Дежурный аналитик пишет: ежедневный отчёт по событиям арендатора
формируется больше минуты, раньше был мгновенным. Данных за ночь не
прибавилось. Ничего не выкатывали.

Тебе выдали доступ к базе стенда. Разберись и почини.

## Запрос отчёта

Этот запрос **менять нельзя** — он зашит в BI-инструмент и приезжает как есть:

```sql
SELECT kind, count(*) AS events
FROM events
WHERE tenant_id = 42
  AND created_at >= TIMESTAMPTZ '2026-01-01'
  AND created_at <  TIMESTAMPTZ '2026-02-01'
GROUP BY kind
ORDER BY kind;
```

## Что считается решённым

1. Запрос возвращает **тот же результат**, что и раньше.
2. Запрос читает **не больше 1000 страниц**. Сейчас он читает около 2560 —
   это вся таблица целиком ради пятисот строк ответа.
3. **Все данные на месте.** Удалять или архивировать события нельзя — это боевые
   данные, отчёт по ним ещё будут строить.

Третий пункт стоит перечитать. Сделать запрос быстрым, удалив половину таблицы,
технически можно — и именно так «чинят» инциденты те, кого потом ищут.

Способ починки не задан намеренно. Проверяется результат, а не то, какую команду
ты набрал: любое решение, после которого отчёт перестаёт перечитывать таблицу,
засчитывается.

## С чего начать

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT kind, count(*) FROM events
WHERE tenant_id = 42
  AND created_at >= TIMESTAMPTZ '2026-01-01'
  AND created_at <  TIMESTAMPTZ '2026-02-01'
GROUP BY kind ORDER BY kind;
```

Число из пункта 2 — это `shared hit` плюс `shared read` в строке `Buffers`
самого верхнего узла плана: там счётчики уже сложены по всему дереву.

Дальше — смотреть, что именно дорого, и почему планировщик выбрал то, что
выбрал. Причина в каждом варианте своя, и **`Seq Scan` — не единственная её
форма**. План, идущий через индекс, тоже умеет прочитать всю таблицу.
