# Разбор

Открывается после сдачи. Если читаешь до — задача перестанет чему-либо учить.

Все числа ниже — настоящие, снятые с этого стенда. Твои могут отличаться на
единицы, но не в разы.

## Общий подход

Первый шаг во всех трёх вариантах одинаков:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT kind, count(*) FROM events
WHERE tenant_id = 42
  AND created_at >= TIMESTAMPTZ '2026-01-01'
  AND created_at <  TIMESTAMPTZ '2026-02-01'
GROUP BY kind ORDER BY kind;
```

Дальше смотрим на три вещи, и каждая отвечает за свой вариант:

1. **Способ доступа** к `events` и по какому индексу.
2. **Расхождение оценки с фактом**: `rows=38689` против `actual rows=485`.
3. **Buffers** — сколько страниц реально прочитано.

Таблица занимает около 2500 страниц. Ответ — 510 строк. Значит, здоровый план
читает сотни страниц, а не тысячи.

## Вариант 1: индекса нет

```
Parallel Seq Scan on events (rows=305) (actual rows=255)
  Rows Removed by Filter: 99745
Buffers: shared hit=2559
```

Оценка совпала с фактом — планировщик не ошибся, у него просто нет другого
пути. Проверяем:

```sql
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'events';
```

Кроме первичного ключа ничего нет. Решение:

```sql
CREATE INDEX events_tenant_created_idx ON events (tenant_id, created_at);
```

**484 страницы** вместо 2559, 0.9 мс вместо 16.6.

**Почему в таком порядке.** В составном индексе первой ставят колонку с
равенством, второй — с диапазоном. При обратном порядке пришлось бы
просматривать индекс по всему диапазону дат, отбирая нужного арендатора уже
после — то есть ровно то, чем болен вариант 3.

## Вариант 2: статистика врёт, а таблица распухла

Здесь два расхождения сразу:

```
Bitmap Heap Scan on events (rows=37011) (actual rows=485)
  Heap Blocks: exact=2588
Buffers: shared hit=2670
```

Индекс `events_tenant_created_idx` **на месте и используется**. План выглядит
правильным. И читает всю таблицу.

Оценка `rows=37011` против факта `485` — статистика помнит прежнее
распределение, когда арендатор 42 занимал почти всё:

```sql
SELECT last_analyze, last_autoanalyze, n_live_tup, n_dead_tup
FROM pg_stat_user_tables WHERE relname = 'events';
```

`last_analyze` старый, автоочистка на таблице выключена, а `n_dead_tup` — почти
двести тысяч. Данные массово переписали одним `UPDATE`, и в PostgreSQL это
означает: старая версия каждой строки осталась в таблице и в индексе.

**Здесь ловушка, ради которой вариант и сделан.** Напрашивающийся ответ:

```sql
ANALYZE events;
```

После него оценка становится верной (`rows=502`), план — правильным, а
страниц по-прежнему **2667**. Лаба не сдаётся, и это не придирка чекера:
запрос действительно не ускорился. Статистика была только половиной беды.
Вторая половина — мёртвые строки: живые пятьсот записей размазаны по всем
страницам таблицы и по всему индексу.

```sql
VACUUM ANALYZE events;
```

**535 страниц.** `VACUUM` возвращает место, занятое мёртвыми версиями,
`ANALYZE` пересобирает статистику. Нужны обе половины.

Засчитывается и другой честный путь — пересобрать распухший индекс:

```sql
REINDEX TABLE events;         -- или CREATE INDEX заново
```

Свежий индекс содержит только живые строки: **463 страницы**. Оба ответа
верны, потому что оба устраняют настоящую причину.

И то, что стоит сделать сверх задачи, иначе через неделю всё повторится:

```sql
ALTER TABLE events SET (autovacuum_enabled = true);
```

Это разница между «починил инцидент» и «починил причину».

## Вариант 3: индекс есть, но не тот

```
Bitmap Heap Scan on events (actual rows=510)
  Filter: (tenant_id = 42)
  Rows Removed by Filter: 20102
  ->  Bitmap Index Scan on events_created_idx (actual rows=20612)
Buffers: shared hit=2565
```

Строка `Rows Removed by Filter: 20102` — весь диагноз. Индекс нашёл 20 612
строк за нужный месяц, из таблицы вытащили все, и 20 102 выбросили, потому что
арендатор не тот. Двадцать тысяч случайных обращений к страницам — это и есть
вся таблица.

```sql
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'events';
-- events_created_idx ... (created_at)
```

Индекс по `created_at`. Селективное условие здесь — `tenant_id` (у арендатора
42 около 2% строк), и его в индексе нет. Месяц из десяти месяцев данных —
десятая часть таблицы, для такой доли индекс по дате бесполезен.

```sql
CREATE INDEX events_tenant_created_idx ON events (tenant_id, created_at);
```

**484 страницы.** Старый индекс можно оставить, если по датам ходят другие
запросы, или удалить, если нет: каждый индекс замедляет запись и занимает место.

```sql
SELECT indexrelname, idx_scan FROM pg_stat_user_indexes WHERE relname = 'events';
```

`idx_scan = 0` за длительный период — кандидат на удаление.

## Ещё быстрее: покрывающий индекс

Во всех трёх вариантах остаётся хвост в четыреста с лишним страниц: индекс
находит нужные строки, но за колонкой `kind` план всё равно идёт в таблицу.
Если добавить её в индекс, ходить в таблицу станет незачем:

```sql
CREATE INDEX events_report_idx ON events (tenant_id, created_at) INCLUDE (kind);
VACUUM ANALYZE events;
```

**6 страниц** вместо 484. В плане появится `Index Only Scan`.

`VACUUM` здесь обязателен: `Index Only Scan` пропускает таблицу, только если
карта видимости говорит, что страница целиком видна всем транзакциям, а
заполняет её именно `VACUUM`. Без него в плане будет `Heap Fetches` с большим
числом, и выигрыш исчезнет. Это частый вопрос на собеседовании.

## Что проверял чекер

1. **Все 200 000 строк на месте.** Ускорить отчёт удалением данных нельзя.
2. **Результат совпал с эталоном**, посчитанным независимым запросом.
3. **Прочитано не больше 1000 страниц** против примерно 2560 в исходном
   состоянии.

Первый пункт стоял не для красоты: удаление старых событий действительно
ускорило бы запрос и действительно является тем, чем инциденты «чинить» нельзя.

Третий пункт сформулирован через страницы, а не через «нет Seq Scan»
намеренно. Проверка на `Seq Scan` пропустила бы варианты 2 и 3: там план идёт
через индекс — и читает всю таблицу.

## Что унести с собой

«Медленный запрос» — не диагноз, а симптом, и причин у него минимум три:
индекса нет, индекс есть не тот, или индекс есть и правильный, но таблица
распухла, а статистика устарела. Лечатся они по-разному, и перепутать легко:
во всех трёх случаях запрос одинаково читает всю таблицу.

Отличить их можно за две минуты:

| Что видно в плане | Причина |
|---|---|
| `Seq Scan`, оценка = факту | индекса нет |
| индекс используется, оценка в разы больше факта, `n_dead_tup` велик | распухание и устаревшая статистика |
| индекс используется, но большой `Rows Removed by Filter` | индекс не по тем колонкам |

И главный навык, который здесь тренируется: смотреть на `Buffers`, а не на имя
узла. Название плана говорит, каким СПОСОБОМ сервер шёл к данным. Сколько он
при этом сделал работы, говорят только страницы.
