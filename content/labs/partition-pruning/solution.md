# Разбор

Открывается после сдачи.

## Решение

Секционировать существующую таблицу на месте нельзя: `PARTITION BY` задаётся
при создании. Поэтому строится новая, данные переносятся, таблицы меняются
местами.

```sql
CREATE TABLE events_new (
    event_id   bigint GENERATED ALWAYS AS IDENTITY,
    tenant_id  integer NOT NULL,
    kind       text NOT NULL,
    created_at timestamptz NOT NULL,
    payload    text NOT NULL
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_01 PARTITION OF events_new
    FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE events_2026_02 PARTITION OF events_new
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
CREATE TABLE events_2026_03 PARTITION OF events_new
    FOR VALUES FROM ('2026-03-01') TO ('2026-04-01');

INSERT INTO events_new (tenant_id, kind, created_at, payload)
SELECT tenant_id, kind, created_at, payload FROM events;

-- Проверить перенос ДО подмены: это то место, где теряют строки.
SELECT (SELECT count(*) FROM events) AS was,
       (SELECT count(*) FROM events_new) AS now;

BEGIN;
DROP TABLE events;
ALTER TABLE events_new RENAME TO events;
COMMIT;

CREATE INDEX ON events (created_at);
ANALYZE events;
```

Границы диапазона — **включая нижнюю и не включая верхнюю**. Февраль это
`FROM ('2026-02-01') TO ('2026-03-01')`, а не `TO ('2026-02-28')`: последний
вариант потеряет события 28 февраля после полудня и весь 29-й в високосный год.

## Что было сломано в каждом варианте

**Вариант 1: секционирования не было.** Прямая задача — спроектировать и
перенести.

**Вариант 2: секционирование по арендатору.** Выглядит осмысленно: запросы
часто фильтруют по `tenant_id`. Но обе беды из инцидента — про время. События
каждого месяца размазаны по всем четырём секциям, поэтому и отсечение по дате
не работает, и удалить месяц отцеплением нельзя.

Урок: **ключ секционирования выбирается под ту задачу, ради которой
секционирование затевалось.** Если это удаление старых данных — ключ обязан
быть временем, даже если фильтруют чаще по другому полю.

**Вариант 3: ключ верный, секция одна — `DEFAULT`.** Отсекать нечего: секция
единственная и читается целиком.

Здесь же ловушка присоединения: пока в `DEFAULT` лежат строки, подходящие под
новый диапазон, присоединить секцию нельзя — PostgreSQL обязан убедиться, что
они не должны были оказаться в ней. Сначала строки переносят, потом
присоединяют:

```sql
CREATE TABLE events_2026_02 (LIKE events INCLUDING ALL);

BEGIN;
WITH moved AS (
    DELETE FROM events_default
    WHERE created_at >= TIMESTAMPTZ '2026-02-01'
      AND created_at <  TIMESTAMPTZ '2026-03-01'
    RETURNING *
)
INSERT INTO events_2026_02 SELECT * FROM moved;

ALTER TABLE events ATTACH PARTITION events_2026_02
    FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');
COMMIT;
```

Изменяющий данные CTE здесь к месту: перенос происходит одной командой, и
промежуточного состояния «строки уже удалены, но ещё не вставлены» не
возникает.

## Зачем всё это на самом деле

Три довода, и «таблица большая» среди них нет.

**Дешёвое удаление.** `DELETE` ста миллионов строк — это часы, распухание и
последующая уборка, причём место возвращается не сразу. `DROP TABLE` секции —
операция над метаданными.

**Отсечение секций.** Работает раньше и дешевле любого индекса: планировщик
исключает секцию, не открывая её файлы.

**Обслуживание по частям.** `VACUUM`, `ANALYZE`, перестроение индексов идут по
секциям. Свежая секция может иметь другие индексы, чем архивные, — это
нормально и полезно.

Если старые данные не удаляются, а запросы точечные, секционирование добавит
сложности без выигрыша.

## Чего делать не следовало

**Секционировать по дню.** Три месяца дадут девяносто секций, а пять лет —
почти две тысячи. Планировщик обязан рассмотреть их все, даже если потом
отсечёт, и планирование простого запроса начнёт стоить дороже выполнения.
Ориентир — десятки и сотни секций, для большинства хранилищ это месяц.

**Потерять строки при переносе.** Сверка количества до подмены таблицы — не
формальность: `INSERT ... SELECT` может тихо не перенести часть строк, если у
новой таблицы окажется ограничение, которого не было у старой.

**Забыть про секции на будущее.** Строка, для которой нет подходящей секции,
вызывает ошибку вставки. Секции создают вперёд заданием по расписанию, а не
руками первого числа. Для этого есть pg_partman.

## Что проверял чекер

1. Все 400 000 строк на месте.
2. Отчёт возвращает тот же результат.
3. Таблица секционирована, и ключ включает время события.
4. В плане месячного отчёта участвует не больше одной секции с данными.
5. Ни одна секция не содержит данных больше чем одного месяца — иначе удалить
   месяц отцеплением невозможно.

Гранулярность чекер не диктует: недельные секции тоже пройдут. Требование
сформулировано через свойство, которое нужно на практике, а не через
конкретную реализацию.
