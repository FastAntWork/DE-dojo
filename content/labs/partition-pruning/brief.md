# Инцидент: чистка истории идёт всю ночь

**Понедельник, планёрка.** Ежемесячное удаление старых событий занимает шесть
часов, всё это время база под нагрузкой, а после чистки место на диске не
освобождается. Заодно месячный отчёт стал медленнее — читает всю таблицу
целиком.

Оба симптома об одном.

## Что есть на стенде

```sql
events (
    event_id   bigint,
    tenant_id  integer,
    kind       text,
    created_at timestamptz,   -- события за январь–март 2026
    payload    text
)
```

Данных 400 000 строк за три месяца.

## Запрос отчёта

Менять его нельзя:

```sql
SELECT kind, count(*)
FROM events
WHERE created_at >= TIMESTAMPTZ '2026-02-01'
  AND created_at <  TIMESTAMPTZ '2026-03-01'
GROUP BY kind;
```

## Задача

Перестроить хранение так, чтобы:

- отчёт за месяц читал **только данные этого месяца**;
- удаление месяца было операцией над метаданными, а не многочасовым `DELETE`.

## Что считается решённым

1. **Таблица секционирована**, и ключ секционирования — время события.
2. **Отсечение работает**: в плане месячного отчёта участвует ровно одна
   секция.
3. **Каждая секция содержит данные только одного месяца.** Иначе удалить месяц
   отцеплением секции не получится — а ради этого всё и затевалось.
4. **Данные на месте** — все 400 000 строк.
5. **Отчёт возвращает верный результат.**

## С чего начать

```sql
-- Как устроена таблица сейчас
\d+ events

-- Что в плане отчёта
EXPLAIN SELECT kind, count(*) FROM events
WHERE created_at >= TIMESTAMPTZ '2026-02-01'
  AND created_at <  TIMESTAMPTZ '2026-03-01'
GROUP BY kind;
```

Секционировать существующую таблицу «на месте» нельзя — придётся создать новую
и перенести данные. Это нормальная работа инженера, и вопрос лишь в том,
как не потерять при этом ни строки.

Причина в каждом варианте своя: где-то секционирования нет вовсе, где-то оно
есть, но не помогает.

## Подключение

Строка подключения выведена рядом с кнопкой запуска. База пересоздаётся при
каждом запуске лабы.
