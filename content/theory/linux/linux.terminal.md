# Linux: терминал, файлы, процессы, диагностика

> Практический минимум. Инженер данных живёт в терминале не потому, что это
> модно, а потому что пайплайн падает на сервере, куда нет графического
> интерфейса.

Тему редко спрашивают напрямую. Её проверяют задачей: «в логе за сутки найди
все ошибки по этому клиенту и посчитай, сколько их». Человек, который ответит
конвейером из трёх команд, и человек, который скачает файл на ноутбук, —
разные кандидаты.

## Что нужно уметь после этого узла

- Искать в больших файлах, не открывая их целиком
- Собирать конвейер и объяснять каждое звено
- Понимать, во что упёрся сервер
- Читать и осмысленно менять права
- Различать переменные окружения и оболочки
- Находить процесс по порту и место на диске

## 1. Философия конвейера

Все команды устроены одинаково: читают из **стандартного ввода**, пишут в
**стандартный вывод**, ошибки — в **стандартный поток ошибок**. Поэтому их
можно соединять.

```bash
cat app.log | grep ERROR | wc -l
```

Три потока имеют номера: `0` — ввод, `1` — вывод, `2` — ошибки. Отсюда
конструкции:

```bash
command > out.txt          # вывод в файл, перезаписав
command >> out.txt         # дописать
command 2> err.txt         # только ошибки
command > all.txt 2>&1     # оба потока в один файл
command 2>/dev/null        # ошибки выбросить
```

Порядок в `> all.txt 2>&1` существенен: сначала вывод перенаправляется в файл,
потом ошибки — «туда же, куда вывод». Обратный порядок даёт другое поведение,
и это классический вопрос с подвохом.

## 2. Поиск в логах

**`grep`** — построчный поиск по образцу.

```bash
grep ERROR app.log                 # строки с ERROR
grep -i error app.log              # без учёта регистра
grep -c ERROR app.log              # только количество
grep -n ERROR app.log              # с номерами строк
grep -v DEBUG app.log              # ВСЁ, КРОМЕ совпадений
grep -A3 -B1 ERROR app.log         # три строки после и одну до
grep -r "tenant_id" ./src          # рекурсивно по каталогу
grep -E "ERROR|FATAL" app.log      # регулярное выражение
```

`-v` и `-A/-B` — то, что чаще всего забывают, а они полезнее прочего: ошибка
без контекста обычно ничего не объясняет.

**`rg` (ripgrep)** делает то же самое в разы быстрее и уважает `.gitignore` —
если он есть на машине, лучше использовать его.

**Чтение больших файлов:**

```bash
head -100 big.log        # первые 100 строк
tail -100 big.log        # последние
tail -f app.log          # следить за дописыванием в реальном времени
less big.log             # листать, не загружая целиком
zcat archive.log.gz | grep ERROR   # искать в сжатом, не распаковывая
```

`tail -f` — основной способ смотреть, что происходит прямо сейчас.
Открывать многогигабайтный файл редактором нельзя: он попытается прочитать его
в память.

## 3. Обработка текста

**`awk`** — построчная работа с колонками. Минимум, который окупается:

```bash
awk '{print $1}' access.log                  # первое поле
awk -F',' '{print $2}' data.csv              # разделитель — запятая
awk '$3 > 100 {print $0}' data.txt           # фильтр по значению
awk '{sum += $2} END {print sum}' data.txt   # сумма колонки
```

**`sort` и `uniq`** — почти всегда вместе, потому что `uniq` схлопывает только
**соседние** одинаковые строки:

```bash
sort file | uniq -c | sort -rn | head -20
```

Этот конвейер стоит запомнить целиком: он отвечает на вопрос «какие значения
встречаются чаще всего» и решает половину задач разбора логов.

**`cut`, `tr`, `sed`:**

```bash
cut -d',' -f1,3 data.csv        # колонки 1 и 3
tr ',' '\t' < data.csv          # заменить символы
sed 's/старое/новое/g' f.txt    # замена по образцу
sed -n '100,200p' big.log       # только строки 100-200
```

Практический пример целиком — «топ-10 клиентов по числу ошибок за сутки»:

```bash
grep ERROR app.log | awk -F'tenant=' '{print $2}' | cut -d' ' -f1 \
  | sort | uniq -c | sort -rn | head -10
```

## 4. Файлы, места и права

```bash
df -h              # свободное место по разделам
du -sh *           # размер каждого объекта в текущем каталоге
du -sh * | sort -h # то же, отсортировано
find . -name "*.log" -size +100M     # найти крупные файлы
find . -mtime +30 -name "*.tmp"      # старше 30 дней
```

`df` показал 100%, а `du` не находит виновника — классическая ситуация. Обычно
это **удалённый файл, который держит открытым процесс**: место не
освобождается, пока процесс жив. Ищется через `lsof | grep deleted`.

**Права** читаются как три группы по три символа:

```
-rw-r--r--   владелец: чтение+запись, группа: чтение, остальные: чтение
drwxr-x---   каталог, владелец: всё, группа: вход и чтение, остальные: ничего
```

```bash
chmod +x script.sh     # сделать исполняемым
chmod 640 secret.env   # владельцу rw, группе r, остальным ничего
chown user:group file
```

Для каталога право `x` означает не «исполнить», а «войти внутрь». Каталог без
`x` нельзя открыть, даже зная имя файла в нём.

**Права 777 — почти всегда ошибка.** Это не «починить доступ», а «отдать всем
всё»; настоящая причина обычно в другом — в отсутствии `x` на промежуточном
каталоге или в неверном владельце.

## 5. Процессы

```bash
ps aux | grep python        # найти процесс
top                         # что ест процессор и память сейчас
htop                        # то же, но удобнее
kill <pid>                  # попросить завершиться (SIGTERM)
kill -9 <pid>               # убить принудительно (SIGKILL)
```

Разница между `kill` и `kill -9` содержательная: первый сигнал программа может
перехватить и корректно закрыть файлы и соединения; второй не перехватывается
вовсе. Начинают всегда с обычного `kill`, `-9` — когда не отвечает.

**Что смотреть в `top`:**

- **load average** — среднее число процессов в очереди за 1, 5, 15 минут.
  Сравнивать надо с числом ядер: 4 на четырёхъядерной машине — полная
  загрузка, на однопроцессорной — троекратная перегрузка.
- **%CPU** и **%MEM** по процессам;
- **wa** (iowait) — доля времени ожидания диска. Высокое значение при низком
  проценте процессора означает, что упёрлись в диск, а не в вычисления.

**Кто занял порт:**

```bash
ss -ltnp | grep 5432       # какой процесс слушает
lsof -i :5432              # то же другим инструментом
```

Ровно эта задача возникает, когда стек не поднимается из-за занятого порта.

## 6. Переменные окружения

```bash
echo $HOME              # прочитать
export API_URL=http://x # объявить для процесса и всех дочерних
env | sort              # все переменные окружения
VAR=1 command           # только для одного запуска
```

Разница: обычная переменная (`x=1`) живёт в текущей оболочке, а `export`
делает её видимой запускаемым программам. Скрипт, не видящий переменную, —
почти всегда следствие пропущенного `export`.

**`PATH`** — список каталогов, где ищутся команды. Ошибка «command not found»
при явно установленной программе означает, что её каталога нет в PATH.
Проверяется через `which имя` или `command -v имя`.

**Секреты в переменных окружения** видны в `ps` и попадают в историю оболочки.
Для настоящих секретов нужны файлы с правами 600 или хранилище секретов.

## 7. Скрипты

```bash
#!/usr/bin/env bash
set -euo pipefail
```

Три флага, которые надо ставить всегда:

- `-e` — прервать при первой ошибке. Без него скрипт продолжит работать после
  падения команды, и загрузка «успешно» завершится на пустых данных.
- `-u` — считать ошибкой обращение к необъявленной переменной. Защищает от
  классического `rm -rf "$DIR/"`, где `DIR` пуст.
- `-o pipefail` — считать конвейер упавшим, если упало любое звено, а не
  только последнее.

Кавычки вокруг переменных (`"$file"`) обязательны: без них имя с пробелом
разъедется на два аргумента.

## 8. Что ещё пригодится

```bash
ssh user@host              # подключиться
scp file user@host:/path   # скопировать
rsync -av src/ dst/        # синхронизировать, докачивая
nohup command &            # запустить и не потерять при отключении
tmux                       # сессия, переживающая обрыв связи
crontab -e                 # расписание задач
watch -n2 'df -h'          # повторять команду каждые 2 секунды
```

`tmux` (или `screen`) — то, без чего долгая загрузка обрывается вместе с
соединением. Привычка запускать всё длительное внутри сессии экономит часы.
