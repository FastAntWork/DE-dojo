# Модульные тесты: pytest, фикстуры, моки

> Конспект по документации pytest и практике тестирования пайплайнов данных.

В вакансиях тестирование отдельной строкой встречается редко, зато Git и CI/CD —
в 63% и 25%. Смысл прямой: код, который нельзя проверить автоматически, нельзя и
выкатывать регулярно. Для инженера данных у темы есть своя специфика — проверять
приходится не только код, но и сами данные.

## Что нужно уметь после этого узла

- Написать тест, который проверяет поведение, а не реализацию
- Выбрать область видимости фикстуры и понимать цену scope=session
- Разложить сценарий в parametrize вместо копирования тела теста
- Замокать зависимость и назвать признак, по которому мок становится вредным
- Объяснить, почему тест без ассерта ничего не проверяет

## 1. Что делает тест полезным

Тест окупается, когда он **ловит поломку и не мешает изменениям**. Оба свойства
одинаково важны: тест, который краснеет при каждом безобидном рефакторинге, —
это налог, а не защита.

Отсюда главное различие темы.

**Тест поведения** проверяет наблюдаемый результат: на такой вход — такой выход,
такое состояние, такая ошибка.

**Тест реализации** проверяет, как именно функция это сделала: какие методы
вызвала, в каком порядке.

```python
# реализация — плохо
def test_saves_user(mocker):
    repo = mocker.Mock()
    UserService(repo).register("ivan@example.com")
    assert repo.save.called  # зелёный, но не проверяет ничего


# поведение — хорошо
def test_saves_user():
    repo = InMemoryUserRepo()
    UserService(repo).register("ivan@example.com")
    assert repo.get_by_email("ivan@example.com") is not None
```

Первый тест останется зелёным, если в `save` уедет пустой объект или неверный
адрес, и покраснеет при безобидном переименовании метода. То есть он ошибается в
обе стороны — худший из возможных вариантов.

Простой признак: **если тест сломается от рефакторинга, не меняющего поведение,
он проверяет не то.**

---

## 2. Структура теста

Три части, разделённые пустыми строками: подготовка, действие, проверка. Их
принято называть arrange–act–assert.

```python
def test_chunked_splits_evenly():
    items = [1, 2, 3, 4]  # подготовка

    result = list(chunked(items, 2))  # действие

    assert result == [[1, 2], [3, 4]]  # проверка
```

Правила, которые стоит держать:

**Один тест — одно утверждение о поведении.** Не обязательно один `assert`, но
одна проверяемая мысль. Тест, падающий по десяти причинам, не отвечает на вопрос
«что сломалось».

**Имя описывает поведение, а не функцию.** `test_returns_empty_list_for_empty_input`
полезнее, чем `test_chunked_2`: при падении имя видно первым, и оно должно
объяснять, что именно не работает.

**Тест не должен зависеть от других тестов и от порядка запуска.** Проверяется
запуском `pytest -p no:randomly` в разном порядке или просто одного теста
отдельно.

## 3. Фикстуры и их область видимости

Фикстура — подготовленное состояние, которое pytest передаёт тесту по имени
аргумента.

```python
@pytest.fixture
def sample_orders() -> list[Order]:
    return [Order(id=1, total=100), Order(id=2, total=200)]


def test_total_revenue(sample_orders):
    assert total_revenue(sample_orders) == 300
```

`scope` определяет, как часто фикстура пересоздаётся: `function` (по умолчанию),
`class`, `module`, `session`.

**Компромисс, который надо понимать.** Поднять контейнер с базой на каждый тест —
честно, но медленно: десять тестов превращаются в минуты. Поднять один раз на
сессию — быстро, но состояние протекает между тестами, и порядок запуска начинает
влиять на результат.

Рабочая схема для тестов с базой — **разделить дорогое и изменяемое**:

- контейнер и схема — `scope="session"`, поднимаются один раз;
- данные — `scope="function"`: каждый тест выполняется в транзакции, которая
  откатывается после него, либо чистит таблицы перед собой.

Именно так устроены интеграционные тесты в этом проекте: контейнер общий, а схема
сбрасывается перед каждым тестом.

`conftest.py` — место для фикстур, общих для каталога. Импортировать его не надо,
pytest подхватывает сам.

> Источник: pytest documentation, «How to use fixtures» —
> https://docs.pytest.org/en/stable/how-to/fixtures.html

## 4. Параметризация

Один сценарий, много данных — не копированием тела, а `parametrize`:

```python
@pytest.mark.parametrize(
    ("value", "expected"),
    [(0, "ноль"), (1, "один"), (-1, "отрицательное")],
)
def test_describe(value: int, expected: str) -> None:
    assert describe(value) == expected
```

Почему это лучше цикла с `assert` внутри одного теста:

- **каждый набор — отдельный тест** со своим именем, и падение показывает
  конкретный случай;
- **остальные наборы продолжают проверяться**, а цикл остановился бы на первом
  же несовпадении;
- **статистика честная**: три проверки, а не одна.

> Источник: pytest documentation, «Parametrizing tests» —
> https://docs.pytest.org/en/stable/how-to/parametrize.html

## 5. Моки: когда нужны и когда вредят

Мок заменяет настоящую зависимость подделкой. Уместен там, где настоящую вызвать
нельзя или дорого: внешний API, отправка письма, текущее время, случайность.

**Когда мок становится вредным:**

1. **Мокается то, что можно взять по-настоящему.** Для базы есть контейнер,
   для файлов — `tmp_path`. Мок здесь заменяет проверку на её имитацию.
2. **Проверяется факт вызова мока, а не результат.** Разбиралось в первом
   разделе: тест закрепляет реализацию.
3. **Моков в тесте больше двух-трёх.** Это сигнал не о тестах, а о коде: у
   функции слишком много зависимостей, и её стоит разделить.

Часто лучше мока — **подставная реализация**: класс с тем же интерфейсом, хранящий
данные в памяти. `InMemoryUserRepo` из первого примера читается как обычный код и
проверяет результат, а не вызовы.

Отдельный случай — **время**. Функция, вызывающая `datetime.now()` внутри,
непроверяема. Лечится передачей времени аргументом или через `freezegun`. Первое
предпочтительнее: оно делает зависимость явной.

## 6. Что проверять инженеру данных

Специфика профессии: проверять приходится и код, и данные.

**Код** — обычными модульными тестами: чистые функции трансформации, разбор
форматов, вычисление ключей и хешей. Эти тесты быстрые и не требуют IO.

**Пайплайн** — интеграционными: поднять базу в контейнере, прогнать загрузку на
маленьком наборе, проверить результат. Медленнее, но именно здесь ловятся ошибки
в SQL.

**Данные** — проверками качества, а не тестами: количество строк не упало вдвое,
ключ уникален, обязательное поле не пустое, распределение не уехало. Для этого
есть отдельные инструменты — Great Expectations, Soda Core, тесты dbt, — и они
встретились в 63% разобранных вакансий. Это отдельная тема, но связь с
тестированием прямая: и то и другое — автоматическая проверка предположений.

Правило, экономящее часы отладки: **любая ошибка, найденная в проде, сначала
воспроизводится тестом, и только потом чинится.** Иначе нет доказательства, что
она исправлена, и нет защиты от её возвращения.
