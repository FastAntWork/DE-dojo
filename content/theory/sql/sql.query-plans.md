# SQL: планы запросов и как их читать

> Конспект по документации PostgreSQL 16, разделы «Using EXPLAIN» и «Planner
> Cost Constants».

Умение читать план — то, что отличает «пишу запросы» от «отвечаю за них».
Оптимизация запросов названа требованием в трети вакансий, и спрашивают там не
определения, а разбор конкретного плана.

## Что нужно уметь после этого узла

- Прочитать вывод EXPLAIN (ANALYZE, BUFFERS) и назвать самый дорогой узел
- Отличить оценку планировщика от факта и понять, о чём говорит расхождение
- Объяснить, когда Seq Scan быстрее Index Scan, и почему планировщик прав
- Различить Nested Loop, Hash Join и Merge Join и сказать, где какой уместен
- Найти по плану причину медленного запроса и назвать конкретное исправление

---

## 1. Что такое план и откуда он берётся

SQL описывает **что** нужно получить, но не **как**. Как — решает планировщик.
Он перебирает варианты исполнения, оценивает стоимость каждого и выбирает
дешёвый. Оценка строится на статистике: сколько строк в таблице, как
распределены значения в колонках, насколько они уникальны.

Отсюда следствие, которое объясняет большинство внезапных замедлений:
**планировщик не знает ваши данные — он знает их статистику**. Устарела
статистика — решения принимаются по неверной картине мира.

Три команды, которые нужны ежедневно:

- `EXPLAIN запрос` — показать план, ничего не выполняя. Быстро и безопасно.
- `EXPLAIN ANALYZE запрос` — **выполнить** и показать план с фактическими
  числами. Осторожно: `UPDATE` и `DELETE` действительно выполнятся, поэтому их
  разбирают внутри транзакции с откатом.
- `EXPLAIN (ANALYZE, BUFFERS)` — то же плюс сколько страниц прочитано из кеша и
  с диска. Именно `BUFFERS` отвечает на вопрос «запрос медленный сам по себе или
  просто читает много данных».

> Источник: PostgreSQL 16 Documentation, «Using EXPLAIN» —
> https://www.postgresql.org/docs/16/using-explain.html

## 2. Как читать вывод

План — это дерево. Читается **изнутри наружу и снизу вверх**: самые вложенные
узлы выполняются первыми, их результат поднимается к родителю.

```
Sort  (cost=31.39..31.41 rows=7 width=12) (actual time=0.05..0.05 rows=6 loops=1)
  Sort Key: created_at
  ->  Bitmap Heap Scan on orders  (cost=4.48..31.29 rows=7 width=12)
        Recheck Cond: (customer_id = 1234)
        ->  Bitmap Index Scan on orders_customer_idx  (cost=0.00..4.48 rows=7)
              Index Cond: (customer_id = 1234)
```

Что означают числа:

- **cost=4.48..31.29** — оценка в условных единицах. Первое число — стоимость
  получения первой строки, второе — всех. Разница важна: узел с дешёвым стартом
  выгоден под `LIMIT`.
- **rows=7** — сколько строк планировщик **ожидает**.
- **actual time=0.05..0.05 rows=6 loops=1** — что получилось на самом деле.
- **loops** — сколько раз узел выполнялся. **Время и строки в `actual` указаны
  на один проход**, поэтому при `loops=1000` их надо умножать. Это самая частая
  ошибка при чтении плана.

Единицы `cost` — не миллисекунды и не байты. Сравнивать их с `actual time`
бессмысленно. Сравнивать между собой узлы одного плана — осмысленно.

## 3. Главный вопрос: оценка против факта

```
Seq Scan on events  (cost=0.00..18334.00 rows=100 width=42)
                    (actual time=0.02..842.11 rows=1200000 loops=1)
```

Планировщик ждал сто строк, получил миллион двести тысяч. **Расхождение на
порядки — самое важное, что можно увидеть в плане**, потому что все решения выше
по дереву приняты исходя из ошибочного предположения. Он выбрал Nested Loop,
рассчитывая на сто итераций, а получил миллион.

Что делать, по порядку:

1. **`ANALYZE таблица`** — пересобрать статистику. Часто этого достаточно.
2. Проверить, не мешает ли **выражение вокруг колонки**: по `date(created_at)`
   статистики нет, есть только по `created_at`.
3. Проверить **коррелированные условия**. Планировщик считает условия
   независимыми, поэтому `WHERE city = 'Москва' AND region = 'Москва'` даёт
   заниженную оценку. Лечится расширенной статистикой:
   `CREATE STATISTICS ... (dependencies) ON city, region FROM ...`.

Обратная ситуация — оценка совпала с фактом, а запрос медленный — означает, что
дело не в плане, а в объёме: читается ровно столько, сколько нужно, просто этого
много.

## 4. Способы доступа к таблице

**Seq Scan** — читать таблицу подряд. Кажется примитивным, но часто это лучший
выбор: последовательное чтение с диска в разы быстрее случайного, а планировщик
это учитывает через `seq_page_cost` (1.0) и `random_page_cost` (4.0 по
умолчанию, для SSD обычно снижают до 1.1).

**Index Scan** — идти по индексу и за каждой строкой обращаться к таблице.
Выгоден при высокой селективности: когда отбираются проценты строк, а не десятки
процентов.

**Bitmap Index Scan + Bitmap Heap Scan** — компромисс: сначала по индексу
собирается битовая карта нужных страниц, потом страницы читаются по порядку.
Выигрывает на средней селективности, где чистый Index Scan уже даёт слишком
много случайных обращений.

**Index Only Scan** — данные берутся прямо из индекса, к таблице обращений нет.
Возможен, когда все нужные колонки есть в индексе. Самый быстрый вариант, ради
которого делают покрывающие индексы через `INCLUDE`.

**Поэтому «добавить индекс» — не ответ, а гипотеза.** Начиная примерно с
5–10% отбираемых строк Seq Scan выигрывает, и планировщик, выбравший его, чаще
всего прав.

---

## 5. Что мешает использовать индекс

Самая частая причина — **выражение вокруг колонки**. Условие должно быть
sargable, то есть пригодным для поиска по индексу: колонка слева, в чистом виде.

| Не сработает | Сработает |
|---|---|
| `date(created_at) = '2024-03-15'` | `created_at >= '2024-03-15' AND created_at < '2024-03-16'` |
| `upper(email) = 'A@B.C'` | индекс по выражению: `CREATE INDEX ... (upper(email))` |
| `amount * 2 > 100` | `amount > 50` |
| `col LIKE '%текст%'` | триграммный индекс `pg_trgm` |

Разница видна в цифрах: на трёхстах тысячах заказов первый вариант даёт
`Parallel Seq Scan` стоимостью около 5700, второй — `Bitmap Index Scan`
стоимостью около 730. Восьмикратная разница на ровном месте.

Вторая причина — **несовпадение типов**, из-за которого возникает приведение и
условие перестаёт быть sargable. Третья — **низкая селективность**: индекс есть,
но выборка слишком широкая, и планировщик сознательно его игнорирует.

## 6. Три способа соединения

**Nested Loop** — для каждой строки внешней таблицы искать пары во внутренней.
Хорош, когда внешняя сторона мала, а по внутренней есть индекс: десять
обращений по индексу дешевле любой альтернативы. Катастрофичен, когда оценка
внешней стороны занижена: вместо десяти итераций получается миллион.

**Hash Join** — построить хеш-таблицу по меньшей стороне, пройти по большей.
Лучший выбор для сопоставимых объёмов без индексов. Требует памяти: если хеш не
влезает в `work_mem`, он разбивается на пакеты с записью на диск, и это видно в
плане как `Batches: 8` вместо единицы — верный признак, что стоит поднять
`work_mem`.

**Merge Join** — слить две отсортированные последовательности. Выгоден, когда
обе стороны уже отсортированы по ключу соединения, например берутся по индексу.
Иначе требует сортировки, которая обычно съедает выигрыш.

## 7. Порядок разбора медленного запроса

Последовательность, которая экономит часы:

1. **`EXPLAIN (ANALYZE, BUFFERS)`**, а не просто `EXPLAIN`. Без фактических
   чисел разговор беспредметен.
2. **Найти узел с наибольшим фактическим временем.** Помнить про `loops`:
   время указано на один проход.
3. **Сравнить `rows` оценки и факта** у этого узла и ниже. Расхождение в разы —
   проблема статистики, а не индексов.
4. **Посмотреть `Buffers`.** Много `read` при малом `hit` — данные не в кеше;
   много страниц вообще — читается лишнее.
5. **Только теперь думать про индексы** — и формулировать не «добавить индекс»,
   а «условие по X несargable из-за функции» или «не хватает индекса по (a, b)
   для этого соединения».

Формулировка «запрос медленный, добавим индекс» — не ответ инженера. Ответ
звучит так: «самый дорогой узел — Hash Join с восемью пакетами, потому что
work_mem 4 МБ, а хеш требует 30; либо поднимаем work_mem для этой сессии, либо
сокращаем выборку до соединения».
