## 1. Порядок вычисления запроса

Главная идея всего узла: **порядок, в котором ты пишешь части запроса, не совпадает
с порядком, в котором они вычисляются**. Из этого несовпадения растёт большинство
ошибок новичка, и почти на каждом собеседовании есть вопрос, который его проверяет.

Документация описывает обработку `SELECT` как последовательность шагов. В
сокращении, оставив то, что встречается ежедневно:

1. Вычисляются запросы из `WITH`.
2. Вычисляются элементы `FROM` — таблицы и соединения. На выходе получается
   «широкая» таблица со всеми колонками всех источников.
3. `WHERE` выбрасывает строки, не удовлетворяющие условию.
4. `GROUP BY` схлопывает строки в группы, затем `HAVING` выбрасывает целые группы.
5. **Только теперь** вычисляются выражения из списка `SELECT`.
6. `DISTINCT` убирает дубликаты.
7. Применяются `UNION`, `INTERSECT`, `EXCEPT`.
8. `ORDER BY` сортирует результат.
9. `LIMIT` и `OFFSET` отрезают нужный кусок.

Обрати внимание на разрыв между шагами 3 и 5. Когда выполняется `WHERE`, колонок,
которые ты описал в `SELECT`, ещё не существует — они появятся на два шага позже.

Практическое следствие для производительности: чем раньше отсекаются строки, тем
меньше работы у всего, что идёт следом. Условие, которое можно поставить в `WHERE`,
не стоит откладывать до `HAVING` — в `WHERE` оно отработает до группировки и
сократит объём данных, которые придётся группировать.

> Источник: PostgreSQL 16 Documentation, «SELECT», раздел Description —
> https://www.postgresql.org/docs/16/sql-select.html

## 2. Где можно ссылаться на псевдоним, а где нельзя

Документация формулирует правило дословно:

> «An output column's name can be used to refer to the column's value in `ORDER BY`
> and `GROUP BY` clauses, but not in the `WHERE` or `HAVING` clauses; there you must
> write out the expression instead.»

То есть псевдоним из `SELECT` доступен в `ORDER BY` и в `GROUP BY`, но **недоступен
в `WHERE` и `HAVING`**. Это ровно то, что следует из порядка вычисления: `ORDER BY`
идёт после `SELECT`, а `WHERE` и `HAVING` — до.

Не работает:

```sql
SELECT price * qty AS total
FROM order_items
WHERE total > 1000;          -- ERROR: column "total" does not exist
```

Работает:

```sql
SELECT price * qty AS total
FROM order_items
WHERE price * qty > 1000     -- выражение повторено целиком
ORDER BY total;              -- а здесь псевдоним уже существует
```

Если повторять длинное выражение не хочется — оберни запрос в подзапрос или CTE,
тогда на внешнем уровне псевдоним станет обычной колонкой.

`GROUP BY` — исключение из логики шагов: он умеет ссылаться на выходную колонку по
имени или по порядковому номеру, хотя формально вычисляется раньше `SELECT`. В
документации это оговорено отдельно. Полагаться на порядковые номера (`GROUP BY 1, 2`)
в рабочем коде не стоит: при вставке колонки в `SELECT` запрос молча начнёт
группировать по другому.

> Источник: PostgreSQL 16 Documentation, «SELECT», разделы Description и
> GROUP BY Clause — https://www.postgresql.org/docs/16/sql-select.html

## 3. NULL и трёхзначная логика

`NULL` в SQL означает не «пусто» и не «ноль», а «значение неизвестно». Отсюда
следует главное: **любое сравнение с NULL даёт не TRUE и не FALSE, а NULL** —
третье логическое значение, которое в документации называется unknown.

`WHERE` пропускает дальше только те строки, для которых условие дало TRUE. Строки
с unknown отбрасываются наравне с FALSE. Поэтому:

```sql
SELECT count(*) FROM employees WHERE manager_id = NULL;   -- всегда 0
SELECT count(*) FROM employees WHERE manager_id IS NULL;  -- то, что нужно
```

Первый запрос не вернёт ничего никогда, независимо от данных, и при этом не выдаст
ошибку — самый неприятный вид бага.

Та же ловушка бьёт по `NOT IN`, когда в подзапросе встречается NULL:

```sql
SELECT * FROM customers
WHERE id NOT IN (SELECT customer_id FROM orders);  -- пусто, если есть NULL
```

Выражение разворачивается в цепочку `id <> v1 AND id <> v2 AND ... AND id <> NULL`.
Последнее слагаемое даёт unknown, а `AND` с unknown уже не может дать TRUE. Итог —
пустой результат. Поэтому anti-join пишут через `NOT EXISTS`, который такой
проблемы не имеет.

Отдельно стоит запомнить два места, где NULL ведёт себя **не** по этому правилу:

- `DISTINCT` и `GROUP BY` считают все NULL-значения одинаковыми и схлопывают их в
  одну группу, хотя `NULL = NULL` даёт unknown.
- Агрегатные функции игнорируют NULL: `count(колонка)` считает только непустые
  значения, в отличие от `count(*)`, который считает строки. По той же причине
  `avg()` делит сумму на число непустых значений, а не на число строк — типичная
  причина расхождения «среднего» в отчётах.

> Источники: PostgreSQL 16 Documentation, «Comparison Functions and Operators» —
> https://www.postgresql.org/docs/16/functions-comparison.html;
> «Aggregate Functions» — https://www.postgresql.org/docs/16/functions-aggregate.html

## 4. DISTINCT против GROUP BY

На одной колонке `SELECT DISTINCT dept FROM employees` и
`SELECT dept FROM employees GROUP BY dept` возвращают одинаковый набор значений,
включая ровно один NULL. Разница не в результате, а в возможностях:

- `GROUP BY` открывает доступ к агрегатам (`count`, `sum`, `avg`) и к `HAVING`.
- `DISTINCT` только убирает дубликаты строк целиком — по **всем** колонкам списка
  `SELECT`, а не по первой. Это частое заблуждение: `SELECT DISTINCT a, b` не
  оставляет по одной строке на каждое `a`.

Утверждать, что один из них быстрее, нельзя: план зависит от статистики, размера
таблицы и наличия индексов. Оба обычно выполняются либо через сортировку, либо
через хеширование, и выбор делает планировщик. Проверяется это `EXPLAIN`, а не
поверьями — этим займёмся в узле `sql.query-plans`.

В PostgreSQL есть ещё `DISTINCT ON (выражение)` — расширение, которого нет в
стандарте. Оно оставляет первую строку из каждой группы по указанному выражению,
и «первая» определяется `ORDER BY`. Без явного `ORDER BY` результат будет
недетерминированным.

> Источник: PostgreSQL 16 Documentation, «SELECT», раздел DISTINCT Clause —
> https://www.postgresql.org/docs/16/sql-select.html

## 5. Сортировка и выборка куска

Два правила, которые стоят потерянных вечеров:

**`LIMIT` без `ORDER BY` не имеет смысла.** Документация прямо предупреждает: без
сортировки порядок строк не определён, поэтому `LIMIT 10` вернёт «какие-то десять
строк», и на разных запусках они могут отличаться. Особенно коварно то, что на
маленькой таблице результат кажется стабильным.

**`ORDER BY` должен быть однозначным.** Если сортировка не определяет порядок
полностью — например, сортируешь по дате, а в дате есть дубликаты — порядок внутри
группы одинаковых значений произволен. При пагинации через `OFFSET` это приводит к
тому, что одна и та же строка попадает на две страницы, а другая исчезает.
Лечится добавлением уникальной колонки последним ключом сортировки:
`ORDER BY created_at DESC, id DESC`.

По умолчанию `ORDER BY` сортирует по возрастанию, а NULL считаются больше любого
значения (`NULLS LAST` при `ASC`). Это поведение можно изменить явно:
`ORDER BY x ASC NULLS FIRST`.

> Источник: PostgreSQL 16 Documentation, «SELECT», разделы ORDER BY Clause и
> LIMIT Clause — https://www.postgresql.org/docs/16/sql-select.html
