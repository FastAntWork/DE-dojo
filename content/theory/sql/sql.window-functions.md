# SQL: оконные функции

> Конспект по документации PostgreSQL 16, разделы «Window Functions» и
> «Window Function Calls».

Оконные функции названы главным различителем на собеседованиях в аналитические
роли. Причина простая: они решают целый класс задач, который без них решается
громоздкими подзапросами, и по владению ими видно, писал ли человек аналитику
или только выборки.

## Что нужно уметь после этого узла

- Объяснить, чем окно отличается от группировки: почему строки не схлопываются
- Прочитать frame clause и предсказать результат ROWS против RANGE при дублях
- Выбрать между ROW_NUMBER, RANK и DENSE_RANK по условию задачи
- Собрать скользящее среднее и накопительный итог без подзапросов
- Объяснить, почему LAST_VALUE без явной рамки возвращает текущую строку

---

## 1. Окно против группировки

`GROUP BY` схлопывает: было десять строк — стала одна. Оконная функция
**оставляет все строки на месте** и приписывает к каждой значение, посчитанное
по её окружению.

```sql
SELECT title, category, price,
       avg(price) OVER (PARTITION BY category) AS avg_in_category
FROM products;
```

Каждый товар остался отдельной строкой, но рядом с ним появилась средняя цена по
его категории. Через `GROUP BY` это потребовало бы группировки и обратного
соединения с исходной таблицей.

Отсюда правило выбора: **нужно свести данные — GROUP BY; нужно обогатить строки
контекстом — окно.** «Доля товара в категории», «место в рейтинге», «отличие от
предыдущего значения» — всё это про окна.

Второе важное следствие: оконные функции вычисляются **после** WHERE, GROUP BY и
HAVING, но **до** ORDER BY и LIMIT. Поэтому в WHERE на результат окна сослаться
нельзя — нужен подзапрос или CTE. Это ровно та же логика, что с псевдонимами в
`sql.core.select`, только на шаг позже.

> Источник: PostgreSQL 16 Documentation, «Window Functions» —
> https://www.postgresql.org/docs/16/tutorial-window.html

## 2. Устройство OVER

```
OVER (PARTITION BY ... ORDER BY ... рамка)
```

- **PARTITION BY** делит строки на независимые группы. Функция считается внутри
  каждой отдельно. Без него всё множество строк — одно окно.
- **ORDER BY** задаёт порядок внутри окна. Нужен там, где важна
  последовательность: нумерация, накопительный итог, обращение к соседям.
- **Рамка** ограничивает, какие строки окна участвуют в расчёте для текущей
  строки.

Одно и то же окно можно назвать один раз и переиспользовать:

```sql
SELECT title,
       row_number() OVER w AS position,
       sum(price)   OVER w AS running
FROM products
WINDOW w AS (PARTITION BY category ORDER BY price DESC);
```

Полезно, когда окон несколько: определение не размножается по запросу, и правка
делается в одном месте.

## 3. Нумерация: три функции, три поведения

Значения 100, 100, 90 при `ORDER BY value DESC`:

| Функция | Результат | Когда нужна |
|---|---|---|
| `row_number()` | 1, 2, 3 | нужен уникальный номер: пагинация, дедупликация |
| `rank()` | 1, 1, 3 | спортивный рейтинг: после двух первых мест идёт третье |
| `dense_rank()` | 1, 1, 2 | уровни без пропусков: категории цен, грейды |

**Ловушка `row_number`:** при равных значениях в ORDER BY порядок между ними не
определён. Один и тот же запрос на одних и тех же данных может выдать разную
нумерацию — особенно после `VACUUM` или при параллельном плане. Если результат
должен быть воспроизводимым, сортировку надо доопределить уникальной колонкой:
`ORDER BY price DESC, id`.

Самое частое применение `row_number` в работе с данными — **дедупликация**:
пронумеровать строки внутри группы дублей и оставить первую.

```sql
WITH numbered AS (
    SELECT *, row_number() OVER (PARTITION BY email ORDER BY updated_at DESC) AS rn
    FROM customers
)
SELECT * FROM numbered WHERE rn = 1;
```

Обрати внимание: фильтр по `rn` вынесен в CTE — в WHERE того же уровня на окно
сослаться нельзя.

## 4. Рамка: самая тонкая часть

Рамка отвечает на вопрос «какие строки окна видит текущая строка». И у неё есть
поведение по умолчанию, которое почти никто не знает наизусть.

**Если ORDER BY в OVER отсутствует** — рамкой является всё окно целиком.
Поэтому `avg(price) OVER (PARTITION BY category)` даёт среднее по всей категории.

**Как только появляется ORDER BY** — включается рамка по умолчанию
`RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, то есть «от начала окна до
текущей строки». Именно поэтому `sum(...) OVER (ORDER BY ...)` даёт
накопительный итог, а не общую сумму — многих это удивляет.

И отсюда же знаменитая ловушка:

```sql
SELECT title, category,
       last_value(price) OVER (PARTITION BY category ORDER BY price) AS top
FROM products;
```

Ожидалась самая высокая цена в категории, а вернулась цена **текущей строки**:
рамка заканчивается на ней, и последняя строка рамки — это она сама. Лечится
явной рамкой:

```sql
OVER (PARTITION BY category ORDER BY price
      ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING)
```

**ROWS против RANGE.** `ROWS` считает физические строки: «две предыдущие» — это
ровно две. `RANGE` считает по значениям: все строки с тем же значением ORDER BY
попадают в рамку целиком.

На данных без дублей они совпадают — и именно поэтому ошибка обычно доживает до
прода, где дубли появляются. Правило: **если не уверен, пиши ROWS** — его
поведение предсказуемо и не зависит от данных.

> Источник: PostgreSQL 16 Documentation, «Window Function Calls» —
> https://www.postgresql.org/docs/16/sql-expressions.html#SYNTAX-WINDOW-FUNCTIONS

## 5. Скользящее окно и соседи

**Скользящее среднее** по трём точкам:

```sql
SELECT day, amount,
       avg(amount) OVER (ORDER BY day ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS ma3
FROM daily_sales;
```

**Обращение к соседям** — `lag()` и `lead()`:

```sql
SELECT day, amount,
       amount - lag(amount) OVER (ORDER BY day) AS delta
FROM daily_sales;
```

У первой строки предыдущей нет, поэтому `lag` вернёт NULL и разница будет
пустой. Если нужен ноль — третьим аргументом задаётся значение по умолчанию:
`lag(amount, 1, 0)`.

Задачи «на сколько выросло к прошлому месяцу», «сколько дней между заказами»,
«найти разрывы в последовательности» — все решаются этой парой функций, и все
регулярно встречаются на собеседованиях.

## 6. Цена

Окно требует сортировки внутри каждой партиции. В плане это видно как узел
`WindowAgg` под `Sort`. На больших объёмах сортировка становится главной
стоимостью запроса, а если данные не помещаются в `work_mem` — уходит на диск,
и это видно в `EXPLAIN (ANALYZE, BUFFERS)` как внешняя сортировка.

Что с этим делают: подходящий индекс позволяет получить данные уже
отсортированными и пропустить шаг сортировки; уменьшение числа партиций и
предварительная фильтрация в WHERE сокращают объём. Разбираться в этом будем в
узле `sql.query-plans` — там же, где научимся читать сам план.
