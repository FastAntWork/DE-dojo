# SQL: агрегация и группировка

> Конспект по документации PostgreSQL 16, разделы «Aggregate Functions» и
> «GROUP BY / HAVING».

## Что нужно уметь после этого узла

- Объяснить разницу между WHERE и HAVING через порядок вычисления запроса

- Собрать условную агрегацию через FILTER или CASE и выбрать осознанно

## 1. Что делает GROUP BY

`GROUP BY` схлопывает строки в группы: все строки с одинаковым значением
группирующих выражений становятся одной строкой результата. После этого к
каждой группе применяются агрегатные функции.

Ключевое следствие, из которого растёт половина ошибок новичка: **в списке
SELECT после группировки может стоять только то, что либо входит в GROUP BY,
либо обёрнуто в агрегат**. Иначе непонятно, какое из нескольких значений внутри
группы показывать, и PostgreSQL честно откажется выполнять запрос.

Исключение — функциональная зависимость от первичного ключа. Если группировать
по `c.id`, то `c.name` можно писать без агрегата: имя однозначно определяется
идентификатором, и сервер это понимает.

## 2. WHERE против HAVING

Оба фильтруют, но на разных шагах вычисления запроса:

```
FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
```

**WHERE отсекает строки до группировки.** Условие на агрегат там написать нельзя
— агрегата ещё не существует.

**HAVING отсекает целые группы после.** Только там можно написать
`count(*) > 5`.

Задача: взять заказы 2024 года и оставить клиентов, у которых таких заказов
больше пяти. Год — в WHERE, количество — в HAVING:

```sql
SELECT customer_id, count(*) AS orders
FROM orders
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01'
GROUP BY customer_id
HAVING count(*) > 5;
```

**Почему это не только про синтаксис.** Условие, которое можно поставить в
WHERE, туда и надо ставить: оно отсечёт строки до группировки, и группировать
придётся меньше данных. Условие, перенесённое в HAVING «чтобы всё было в одном
месте», заставит сервер сгруппировать всё, а потом выбросить лишнее.

## 3. NULL и агрегаты

Правило одно, а следствий много: **агрегатные функции игнорируют NULL**.

| Выражение | Что считает |
|---|---|
| `count(*)` | строки, включая полностью пустые |
| `count(колонка)` | строки, где колонка не NULL |
| `count(DISTINCT колонка)` | различные непустые значения |
| `sum`, `avg`, `min`, `max` | только непустые значения |

Отсюда две ошибки, которые доживают до отчётов руководству.

**Первая: `avg` делит не на то, на что думают.** Если из 100 строк в колонке
`bonus` заполнено 70, то `avg(bonus)` поделит сумму на 70, а не на 100. Иногда
это правильно, иногда нет — но решение должно быть осознанным. Если нужно
считать пустые как нули, это надо написать явно: `avg(coalesce(bonus, 0))`.

**Вторая: `sum` по пустому множеству возвращает NULL, а не ноль.** Не 0 —
именно NULL. Поэтому в витринах пишут `coalesce(sum(...), 0)`, иначе у клиента
без заказов в отчёте окажется пустота вместо нуля.

У `count` такой проблемы нет: он возвращает 0. Эта несимметричность выглядит
странно, но она из стандарта: сумма несуществующих значений не определена, а вот
их количество определено и равно нулю.

> Источник: PostgreSQL 16 Documentation, «Aggregate Functions» —
> https://www.postgresql.org/docs/16/functions-aggregate.html

## 4. Условная агрегация

Задача: одним запросом посчитать всего заказов и сколько из них оплачено.

**Через FILTER — стандартный и читаемый способ:**

```sql
SELECT count(*) AS total,
       count(*) FILTER (WHERE status = 'paid') AS paid
FROM orders;
```

**Через CASE — работает везде, читается хуже:**

```sql
SELECT count(*) AS total,
       count(CASE WHEN status = 'paid' THEN 1 END) AS paid
FROM orders;
```

Оба варианта считаются **за один проход по данным**, и это главное: наивная
альтернатива с двумя подзапросами прочитает таблицу дважды.

Работает `CASE` за счёт того же правила из предыдущего раздела: `CASE` без
`ELSE` возвращает NULL, а `count` пустые значения не считает. Понимание этой
связки — хороший признак того, что правило про NULL усвоено, а не заучено.

`FILTER` появился в PostgreSQL 9.4 и есть не во всех СУБД, поэтому `CASE`
остаётся переносимым запасным вариантом.

## 5. Итоги по нескольким уровням

Обычная задача отчёта: выручка по категориям, по городам, и общий итог — всё в
одном результате. Наивное решение — три запроса и UNION ALL. Есть короче.

**GROUPING SETS** — явный список группировок:

```sql
SELECT category, city, sum(amount)
FROM sales
GROUP BY GROUPING SETS ((category), (city), ());
```

Пустые скобки означают группировку по нулю колонок, то есть общий итог.

**ROLLUP** — иерархия «сверху вниз»: `ROLLUP (a, b)` даёт группировки `(a, b)`,
`(a)` и `()`. Подходит, когда измерения вложены: страна → город → магазин.

**CUBE** — все возможные сочетания: `CUBE (a, b)` даёт `(a, b)`, `(a)`, `(b)`,
`()`. Подходит, когда измерения независимы.

Отличить строку итога от обычной помогает функция `GROUPING()`: она возвращает 1
для колонок, свёрнутых в этой строке. Без неё строка с NULL в категории
неотличима от строки, где категория действительно пуста.

Всё это считается **за один проход** по данным, в отличие от UNION ALL из
нескольких запросов — ради этого механизм и существует.

> Источник: PostgreSQL 16 Documentation, «GROUPING SETS, CUBE, ROLLUP» —
> https://www.postgresql.org/docs/16/queries-table-expressions.html#QUERIES-GROUPING-SETS

## 6. DISTINCT внутри агрегата

`count(DISTINCT user_id)` — уникальные пользователи. Полезно, но стоит дорого:
сервер обязан удержать все различные значения, чтобы их пересчитать, и на
больших объёмах это заметная нагрузка на память.

Если точность до единицы не критична, в PostgreSQL есть приближённые счётчики
(расширение `postgresql-hll`), а в ClickHouse — `uniqCombined` из коробки.
Разница в скорости на миллиардах строк порядковая, а погрешность около процента.
Вопрос «нужна ли вам точность до единицы» — хороший признак инженера,
понимающего цену запроса.
