# SQL: подзапросы и CTE

> Конспект по документации PostgreSQL 16, разделы «WITH Queries» и «Subquery
> Expressions».

## Что нужно уметь после этого узла

- Отличить коррелированный подзапрос от некоррелированного и понимать цену
- Переписать IN-подзапрос через EXISTS и через JOIN, объяснив, когда что уместно
- Собрать рекурсивный CTE для обхода иерархии и не получить бесконечный цикл
- Объяснить, когда CTE становится оптимизационным барьером и что делает MATERIALIZED

---

## 1. Где может стоять подзапрос

Три позиции, и они ведут себя по-разному.

**В `FROM` — производная таблица.** Обычный источник строк, ничем не отличается
от таблицы:

```sql
SELECT * FROM (SELECT id, price * qty AS total FROM order_items) t WHERE total > 1000;
```

Именно так обходится запрет на использование псевдонима в `WHERE`: во внешнем
запросе `total` уже обычная колонка.

**В `WHERE` — предикат.** `IN`, `EXISTS`, сравнение со скалярным подзапросом.

**В `SELECT` — скалярный подзапрос.** Обязан возвращать не больше одной строки и
одной колонки, иначе запрос упадёт в момент выполнения:

```sql
SELECT c.name,
       (SELECT max(created_at) FROM orders o WHERE o.customer_id = c.id) AS last_order
FROM customers c;
```

Удобно, но за это платят: такой подзапрос логически выполняется для каждой
строки внешнего запроса.

## 2. Коррелированный или нет

**Некоррелированный** подзапрос не ссылается на внешний запрос. Он не зависит от
текущей строки, поэтому вычисляется **один раз**:

```sql
SELECT * FROM products WHERE price > (SELECT avg(price) FROM products);
```

**Коррелированный** ссылается на колонку внешнего запроса, поэтому логически
считается **для каждой строки**:

```sql
SELECT * FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);
```

Слово «логически» здесь важно. Планировщик часто переписывает коррелированный
подзапрос в полусоединение или хеш-соединение, и никакого построчного выполнения
не происходит. Но полагаться на это вслепую нельзя: при сложном подзапросе
переписать его он не сможет, и в плане появится `Nested Loop` с `loops`, равным
числу строк внешнего запроса. Проверяется это одним `EXPLAIN`.

## 3. IN, EXISTS и JOIN

Три способа сказать «клиенты, у которых есть заказы»:

```sql
-- IN
SELECT * FROM customers WHERE id IN (SELECT customer_id FROM orders);

-- EXISTS
SELECT * FROM customers c WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- JOIN
SELECT DISTINCT c.* FROM customers c JOIN orders o ON o.customer_id = c.id;
```

Для положительной проверки все три эквивалентны, и планировщик обычно приводит
их к одному плану. Но у них разные подводные камни:

- **`JOIN` требует `DISTINCT`**, если у клиента несколько заказов — иначе строки
  размножатся. А `DISTINCT` на большом результате стоит дорого.
- **`IN` опасен при отрицании.** `NOT IN` с NULL в подзапросе возвращает пустоту
  всегда — разбиралось в узле `sql.joins`. `NOT EXISTS` этой проблемы не имеет.
- **`EXISTS` останавливается на первой найденной строке**, ему не нужен весь
  набор.

Практическое правило: **для проверки существования пиши `EXISTS`**, для
получения колонок из второй таблицы — `JOIN`. `IN` оставляй для коротких
литеральных списков.

> Источник: PostgreSQL 16 Documentation, «Subquery Expressions» —
> https://www.postgresql.org/docs/16/functions-subquery.html

## 4. CTE: читаемость и её цена

`WITH` даёт подзапросу имя. Главная выгода — читаемость: сложный запрос
раскладывается на шаги, которые можно прочесть сверху вниз.

```sql
WITH totals AS (
    SELECT o.id, sum(oi.quantity * oi.price) AS total
    FROM orders o JOIN order_items oi ON oi.order_id = o.id
    GROUP BY o.id
)
SELECT * FROM totals WHERE total > (SELECT avg(total) FROM totals);
```

Здесь CTE ещё и переиспользуется дважды — в выборке и в подзапросе со средним.
Без него пришлось бы дублировать всю группировку.

**Про оптимизационный барьер.** До PostgreSQL 12 любой CTE вычислялся отдельно и
целиком: планировщик не мог протолкнуть в него условие снаружи. Начиная с 12-й
версии CTE, использованный один раз и не содержащий побочных эффектов,
**встраивается** в основной запрос, и условия проваливаются внутрь.

Управлять этим можно явно:

- `WITH x AS MATERIALIZED (...)` — вычислить отдельно, как раньше.
- `WITH x AS NOT MATERIALIZED (...)` — встроить принудительно.

Когда `MATERIALIZED` полезен: CTE используется несколько раз и дорого считается —
тогда однократное вычисление выгоднее повторного встраивания. Когда вреден: CTE
отдаёт много строк, а снаружи стоит узкое условие — материализация не даст
протолкнуть его внутрь, и вместо `Index Scan` получится полный проход.

Именно это — частый ответ на вопрос «почему после переписывания подзапроса в CTE
запрос стал медленнее».

> Источник: PostgreSQL 16 Documentation, «WITH Queries» —
> https://www.postgresql.org/docs/16/queries-with.html

## 5. Рекурсивный CTE

Обход иерархий: сотрудники и начальники, категории и подкатегории, комплектующие
изделия. Структура всегда одна:

```sql
WITH RECURSIVE tree AS (
    -- якорь: с чего начинаем
    SELECT id, name, 1 AS depth
    FROM employees WHERE manager_id = 2

    UNION ALL

    -- рекурсивная часть: ссылается на само имя CTE
    SELECT e.id, e.name, t.depth + 1
    FROM employees e
    JOIN tree t ON e.manager_id = t.id
)
SELECT * FROM tree ORDER BY depth, id;
```

Как это работает: выполняется якорь, его строки складываются в рабочую таблицу.
Затем повторно выполняется рекурсивная часть — но **только по строкам,
добавленным на предыдущем шаге**. Так до тех пор, пока очередной шаг не даст
новых строк.

**Главная опасность — незавершаемость.** Если в данных есть цикл (сотрудник
оказался собственным начальником по цепочке), `UNION ALL` будет производить
строки бесконечно. Три способа защиты:

1. `UNION` вместо `UNION ALL` — дедупликация остановит повторы. Работает, но
   стоит дорого.
2. **Ограничение глубины**: добавить `WHERE depth < 10` в рекурсивную часть.
   Просто и предсказуемо.
3. **Отслеживание пути**: вести массив пройденных идентификаторов и обрывать при
   повторе. Честнее всего, потому что цикл при этом можно обнаружить и показать:

```sql
SELECT e.id, t.path || e.id, e.id = ANY(t.path) AS is_cycle
FROM employees e JOIN tree t ON e.manager_id = t.id
WHERE NOT t.is_cycle
```

Отдельно стоит знать: `RECURSIVE` пишется один раз сразу после `WITH`, даже если
рекурсивных CTE несколько.

## 6. Что выбрать

| Задача | Инструмент |
|---|---|
| Проверить наличие связанных строк | `EXISTS` |
| Проверить отсутствие | `NOT EXISTS` |
| Взять колонки из второй таблицы | `JOIN` |
| Разложить сложный запрос на шаги | CTE |
| Переиспользовать дорогой расчёт | CTE, при необходимости `MATERIALIZED` |
| Обойти иерархию | `WITH RECURSIVE` |
| Одно значение рядом с каждой строкой | скалярный подзапрос или окно |

Последняя строка стоит внимания: многое из того, что раньше писали
коррелированными подзапросами, короче и быстрее решается оконными функциями. Если
подзапрос в `SELECT` считает что-то по «соседним» строкам — почти наверняка это
задача для окна.
