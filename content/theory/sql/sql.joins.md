# SQL: соединения таблиц

> Конспект по документации PostgreSQL 16, разделы «Table Expressions» и
> «Subquery Expressions». Ссылки в конце разделов.

## Что нужно уметь после этого узла

- Выбрать тип соединения по задаче и обосновать выбор, а не перебирать наугад
- Объяснить, почему условие на правую таблицу в WHERE превращает LEFT JOIN в INNER
- Написать anti-join через NOT EXISTS и сказать, чем он лучше NOT IN при NULL
- Оценить, во сколько строк развернётся соединение при связи многие-ко-многим
- Применить self-join для сравнения строк одной таблицы между собой

## 1. Что вообще делает соединение

Соединение берёт две таблицы и для каждой пары строк проверяет условие. Пары,
для которых условие дало TRUE, попадают в результат. Всё остальное — вариации
на тему «что делать со строками, которым пары не нашлось».

- **INNER JOIN** — только пары. Не нашлось — строка исчезает.
- **LEFT JOIN** — все строки левой таблицы; там, где пары нет, колонки правой
  заполняются NULL.
- **RIGHT JOIN** — то же зеркально. На практике почти не встречается: тот же
  запрос читается понятнее, если поменять таблицы местами и написать LEFT.
- **FULL JOIN** — все строки обеих таблиц. Нужен редко, обычно при сверке двух
  источников: «что есть здесь, но нет там, и наоборот».
- **CROSS JOIN** — все пары со всеми. Осмысленно, когда нужно построить полную
  сетку: все дни × все магазины, чтобы потом подтянуть к ней факты.

Правило выбора простое и звучит как вопрос к себе: **что должно случиться со
строкой, у которой нет пары?** Если «исчезнуть» — INNER. Если «остаться с
пустыми полями» — LEFT. Ответ на этот вопрос даёт бизнес-требование, а не вкус.

> Источник: PostgreSQL 16 Documentation, «Joined Tables» —
> https://www.postgresql.org/docs/16/queries-table-expressions.html

## 2. Главная ловушка: условие в WHERE вместо ON

Запрос выглядит правильным и молча возвращает неверный результат:

```sql
SELECT c.id, o.total
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.created_at >= '2024-01-01';   -- клиентов без заказов больше нет
```

Разберём по шагам. Для клиента без заказов LEFT JOIN подставляет NULL во все
колонки `orders`. Дальше WHERE вычисляет `NULL >= '2024-01-01'` — это не FALSE,
а UNKNOWN, и строка отбрасывается. В результате LEFT JOIN превратился в INNER,
а автор запроса об этом не узнал.

Правильно — перенести условие в ON:

```sql
LEFT JOIN orders o
  ON o.customer_id = c.id
 AND o.created_at >= '2024-01-01'
```

**Разница в моменте применения.** Условие в ON участвует в подборе пары: заказы
до 2024 года просто не считаются парой, и клиент остаётся в результате с NULL.
Условие в WHERE применяется к уже собранному результату соединения, когда NULL
уже подставлены.

Для INNER JOIN разницы нет — там строки без пары исчезают в любом случае.
Поэтому привычка «фильтры пишем в WHERE» работает годами и ломается ровно в тот
день, когда кто-то меняет INNER на LEFT.

Проверить себя можно так: **если в WHERE упоминается колонка «необязательной»
стороны LEFT JOIN — почти наверняка это ошибка.** Единственное законное
исключение — намеренная проверка `IS NULL` для поиска строк без пары.

## 3. Anti-join: строки без пары

Задача «клиенты, у которых нет заказов» решается тремя способами, и они не
равноценны.

**NOT EXISTS — рабочий вариант:**

```sql
SELECT c.id
FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);
```

**LEFT JOIN с проверкой на NULL — тоже верно, читается хуже:**

```sql
SELECT c.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;
```

**NOT IN — ловушка:**

```sql
SELECT c.id FROM customers c
WHERE c.id NOT IN (SELECT customer_id FROM orders);
```

Если среди `customer_id` встретится хотя бы один NULL, результат будет **пустым
всегда**. Выражение разворачивается в цепочку `id <> v1 AND id <> v2 AND ... AND
id <> NULL`. Последнее слагаемое даёт UNKNOWN, а `AND` с UNKNOWN не может дать
TRUE — значит, ни одна строка не пройдёт.

Коварство в том, что ошибка появляется не при написании запроса, а в тот день,
когда в данных впервые возникнет NULL. Запрос при этом не падает: он тихо
возвращает пустоту, и отчёт показывает ноль.

Поэтому правило простое: **anti-join пишем через NOT EXISTS**. Он не зависит от
NULL и обычно лучше планируется.

> Источник: PostgreSQL 16 Documentation, «Subquery Expressions» —
> https://www.postgresql.org/docs/16/functions-subquery.html

## 4. Размножение строк

У клиента 3 заказа и 4 обращения в поддержку. Сколько строк вернёт запрос?

```sql
SELECT c.id, o.total, t.subject
FROM customers c
JOIN orders o ON o.customer_id = c.id
JOIN tickets t ON t.customer_id = c.id;
```

Двенадцать. Две независимые ветки «один-ко-многим» от одной таблицы дают
декартово произведение: каждый заказ склеивается с каждым обращением.

Само по себе это не ошибка — ошибка в том, что происходит дальше. Если поверх
такого соединения написать `SUM(o.total)`, сумма окажется вчетверо больше
правды, потому что каждый заказ посчитан четыре раза.

Ошибка коварна тем, что **на маленьких данных она незаметна**: пока у клиентов
по одному обращению, всё сходится. Расхождение проявится, когда данных станет
больше, и искать его будут в бизнес-логике, а не в запросе.

Два способа лечения:

1. **Агрегировать каждую ветку отдельно** до соединения — в подзапросе или CTE.
2. **Не соединять то, что не нужно соединять**: если требуется «клиенты, у
   которых есть и то, и другое», это два `EXISTS`, а не два JOIN.

Признак проблемы, который стоит выработать: **как только в запросе больше одного
соединения «один-ко-многим» от одной таблицы — проверь количество строк до
агрегации.**

## 5. Self-join

Таблица соединяется сама с собой под разными псевдонимами. Нужен, когда
сравниваются строки одной сущности.

Сотрудник и его начальник:

```sql
SELECT e.name, m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.id = e.manager_id;
```

LEFT здесь обязателен: у директора начальника нет, и с INNER он исчез бы из
результата — классическая ошибка в таких запросах.

Второй типичный случай — сравнение соседних строк: найти заказы, сделанные тем
же клиентом в тот же день, дубликаты, разрывы в нумерации. Правда, для многих
таких задач оконные функции короче и быстрее — этим займёмся в
`sql.window-functions`.

## 6. Как читать чужое соединение

Порядок, который экономит время при разборе незнакомого запроса:

1. **Найти ведущую таблицу** — ту, что в FROM. Результат строится вокруг неё.
2. **Для каждого JOIN спросить: строки без пары должны выжить?** Сверить с типом
   соединения.
3. **Проверить WHERE на колонки необязательных сторон** — там прячется
   превращение LEFT в INNER.
4. **Оценить кардинальность**: не появится ли размножение строк перед агрегацией.

Четыре вопроса закрывают почти все ошибки в соединениях, которые встречаются на
практике и на собеседовании.
