# PostgreSQL: секционирование и отсечение партиций

> Конспект по документации PostgreSQL, глава «Table Partitioning».

Секционирование — тема, где легко перепутать причину и следствие. «Таблица
большая, надо секционировать» — не аргумент. Аргументы ниже.

## Что нужно уметь после этого узла

- Назвать настоящие причины секционировать и одну ложную
- Выбрать способ и ключ
- Проверить отсечение по плану
- Объяснить особенности уникальности и внешних ключей
- Удалять старые данные отсоединением партиции
- Заметить, что партиций стало слишком много

---

## 1. Что это такое

Секционированная таблица — это **родительская таблица без данных** и набор
дочерних, каждая из которых хранит свой диапазон или набор значений. Для
приложения это по-прежнему одна таблица: `SELECT` и `INSERT` идут в родителя,
а PostgreSQL сам направляет строки в нужную секцию.

```sql
CREATE TABLE events (
    id         bigint GENERATED ALWAYS AS IDENTITY,
    tenant_id  integer NOT NULL,
    created_at timestamptz NOT NULL,
    payload    jsonb
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_03 PARTITION OF events
    FOR VALUES FROM ('2026-03-01') TO ('2026-04-01');
```

---

## 2. Зачем это делают

**Настоящая причина 1: дешёвое удаление старых данных.** `DELETE` на сто
миллионов строк — это часы работы, распухание таблицы и последующая уборка.
`DROP TABLE` секции или `DETACH PARTITION` — мгновенная операция над
метаданными. Для хранилища с политикой хранения это главный довод.

**Настоящая причина 2: отсечение партиций.** Запрос за март читает только
мартовскую секцию, остальные не открываются вовсе. Работает раньше и дешевле
любого индекса.

**Настоящая причина 3: обслуживание по частям.** `VACUUM`, `ANALYZE`,
перестроение индексов идут по секциям, а не по всей таблице целиком. Свежая
секция может иметь другое хранение и другие индексы, чем архивные.

**Ложная причина: «таблица большая».** Сам по себе размер не аргумент.
PostgreSQL прекрасно работает с таблицами в сотни миллионов строк при
правильных индексах. Если запросы точечные и старые данные не удаляются,
секционирование только добавит сложности.

---

## 3. Способы секционирования

**RANGE** — по диапазону. Основной случай: время. Границы задаются включая
нижнюю и исключая верхнюю.

**LIST** — по перечню значений: регион, тип события, код страны. Подходит,
когда значений мало и они известны.

**HASH** — по остатку от хеша. Равномерно распределяет строки, когда
естественного ключа секционирования нет, но нужно разбить таблицу на части для
параллельной обработки. Отсечение при этом работает только для равенства.

**Ключ выбирается по фильтрам запросов.** Секционировать по колонке, которой
нет в условиях, — значит получить всю сложность и ни одного выигрыша: каждый
запрос будет читать все секции.

**Секция по умолчанию** (`DEFAULT`) принимает строки, не попавшие ни в один
диапазон. Полезна как страховка от потери данных, но у неё есть неприятная
особенность: пока в ней есть строки, подходящие под новый диапазон,
присоединить новую секцию нельзя.

---

## 4. Отсечение партиций

Главный выигрыш, и его надо уметь проверить.

```sql
EXPLAIN SELECT count(*) FROM events
WHERE created_at >= '2026-03-01' AND created_at < '2026-04-01';
```

В плане должна остаться **одна** секция. Если видны все — отсечение не
сработало.

**Почему не срабатывает:**

1. **В условии нет ключа секционирования.** Самая частая причина.
2. **Функция на ключе** — та же беда, что с индексами: `date(created_at) = ...`
   не даёт отсечь.
3. **Ключ сравнивается с параметром, значение которого неизвестно на этапе
   планирования.** Тогда работает отсечение во время выполнения (runtime
   pruning) — в плане оно видно как `Subplans Removed`.
4. **Соединение по ключу секционирования** отсекает не всегда; помогает
   явное условие по диапазону в самом запросе.

---

## 5. Ограничения, о которых спрашивают

**Уникальность.** Уникальный индекс на секционированной таблице обязан
включать **ключ секционирования**. Причина техническая: индексы у каждой
секции свои, и проверить глобальную уникальность без него невозможно.
Практическое следствие: первичным ключом становится не `id`, а пара
`(id, created_at)` — и это меняет модель, а не только DDL.

**Внешние ключи.** Ссылаться на секционированную таблицу можно начиная с
PostgreSQL 12, но ограничения те же: целевой ключ должен включать ключ
секционирования.

**Индексы.** Создаются на родителе и автоматически создаются на всех секциях.
`CREATE INDEX ... ON ONLY` создаёт только на родителе, чтобы затем строить
секционные индексы по одному с `CONCURRENTLY` и присоединять — приём для
боевых таблиц.

---

## 6. Обслуживание

**Создание секций заранее.** Строка, для которой нет подходящей секции,
вызывает ошибку вставки. Поэтому секции создают вперёд — заданием по
расписанию, а не вручную первого числа.

**Отсоединение вместо удаления:**

```sql
ALTER TABLE events DETACH PARTITION events_2025_01 CONCURRENTLY;
-- данные остались в отдельной таблице: можно выгрузить в архив
DROP TABLE events_2025_01;
```

`CONCURRENTLY` не берёт исключительную блокировку родителя — важно для боевой
системы.

**Присоединение существующей таблицы** (`ATTACH PARTITION`) требует проверки,
что все строки попадают в диапазон. Чтобы проверка была мгновенной, на таблицу
заранее вешают ограничение `CHECK`, совпадающее с границами секции.

---

## 7. Сколько партиций

Каждая секция — отдельная таблица со своими индексами и своей строкой в
системном каталоге. Планировщик обязан рассмотреть их все, даже если потом
отсечёт.

**Ориентир: десятки и сотни, а не тысячи.** Суточные секции за пять лет —
почти две тысячи объектов, и планирование простого запроса начинает стоить
дороже выполнения.

Симптомы перебора: выросло время планирования (видно в `Planning Time`),
раздулся системный каталог, `\d+` работает секундами.

Правило выбора гранулярности: **секция должна быть достаточно крупной**, чтобы
её имело смысл обслуживать отдельно, и достаточно мелкой, чтобы её удаление
освобождало заметный объём. Для большинства хранилищ это месяц.

---

## 8. Секционирование и загрузка данных

Приятное следствие для пайплайнов: **подмена секции — атомарная идемпотентная
загрузка периода**.

```sql
-- собрать новую версию месяца в отдельной таблице
CREATE TABLE events_2026_03_new (LIKE events INCLUDING ALL);
-- ... наполнить ...
BEGIN;
ALTER TABLE events DETACH PARTITION events_2026_03;
ALTER TABLE events ATTACH PARTITION events_2026_03_new
    FOR VALUES FROM ('2026-03-01') TO ('2026-04-01');
COMMIT;
```

Читатель видит либо старую версию месяца, либо новую — промежуточного
состояния нет. Это то же самое, что `INSERT OVERWRITE PARTITION` в мире
Hive и Spark.

---

## 9. Что ещё спросят

- **Наследование таблиц** — старый механизм, предшественник секционирования.
  В новых системах не используется.
- **pg_partman** — расширение, автоматизирующее создание и удаление секций по
  расписанию. Избавляет от собственного велосипеда.
- **Секционирование против шардирования.** Секционирование — внутри одного
  сервера; шардирование — по разным серверам. Путать их не стоит: второе
  решает задачу масштабирования, первое — обслуживания и отсечения.
- **Влияние на планы.** Соединение двух секционированных по одному ключу
  таблиц может выполняться посекционно (partitionwise join), что заметно
  дешевле, — но эту возможность надо включать параметром.
