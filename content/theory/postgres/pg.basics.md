## 1. psql — рабочий инструмент, а не запасной

Графический клиент удобен для разглядывания данных, но всё, что связано с
диагностикой и автоматизацией, делается в psql. На проде он часто единственное,
что доступно.

```bash
psql "postgresql://user:pass@host:5432/dbname"
psql -h host -U user -d dbname          # пароль спросит
```

Команды, которые нужны ежедневно. Все начинаются с обратной косой черты и не
являются SQL — их разбирает сам psql:

| Команда | Что делает |
|---|---|
| `\l` | список баз |
| `\dt` | таблицы текущей схемы |
| `\d таблица` | структура: колонки, типы, индексы, ограничения |
| `\d+ таблица` | то же плюс размер и описание |
| `\di` | индексы |
| `\df` | функции |
| `\dn` | схемы |
| `\timing on` | показывать время каждого запроса |
| `\x` | вертикальный вывод — спасение для широких таблиц |
| `\e` | открыть редактор для длинного запроса |
| `\copy` | загрузить или выгрузить CSV **на стороне клиента** |
| `\q` | выход |

Два приёма, экономящих время:

**`\copy` против `COPY`.** `COPY` читает файл на сервере и требует прав
суперпользователя. `\copy` работает с файлом на вашей машине и прав не требует.
Для выгрузки результата в CSV это основной способ:

```
\copy (SELECT * FROM orders WHERE status = 'paid') TO 'paid.csv' CSV HEADER
```

**Неинтерактивный запуск** для скриптов: `psql -c "SELECT ..."` выполнит один
запрос, `-f файл.sql` — файл, `-tA` уберёт заголовки и выравнивание, чтобы
результат можно было передать дальше по конвейеру.

> Источник: PostgreSQL 16 Documentation, «psql» —
> https://www.postgresql.org/docs/16/app-psql.html

## 2. Кластер, база, схема

Три уровня, которые постоянно путают.

**Кластер** — один экземпляр PostgreSQL, слушающий порт. Внутри него несколько
баз.

**База данных** — изолированная единица. Соединение открывается к конкретной
базе, и **запрос не может выйти за её пределы**: соединить таблицы из двух баз
одним запросом нельзя без внешних механизмов (`postgres_fdw`, `dblink`).

**Схема** — пространство имён внутри базы. Таблицы из разных схем одной базы
прекрасно соединяются в одном запросе:

```sql
SELECT * FROM staging.orders JOIN core.customers ON ...;
```

Схемы — это то, чем в хранилищах разделяют слои: `raw`, `staging`, `core`,
`marts`. Права выдаются на схему целиком, поэтому доступ аналитика к витринам без
доступа к сырью настраивается естественно.

**`search_path`** — список схем, в которых ищется таблица, если схема не указана
явно. По умолчанию `"$user", public`.

```sql
SHOW search_path;
SET search_path TO core, public;
```

Отсюда частая путаница: одна и та же команда `SELECT * FROM orders` у двух
пользователей может обращаться к разным таблицам. В скриптах и миграциях схему
лучше писать явно — так однозначнее.

## 3. Типы данных, которые надо выбрать правильно

**Время.** Главный выбор узла.

`timestamp` хранит «показания часов» без привязки к поясу. `timestamptz`
хранит момент на оси времени: значение приводится к UTC при записи и к часовому
поясу сессии при чтении. Оба занимают 8 байт, и **ни один не хранит имя пояса** —
вопреки названию.

Практическое следствие: два сервера в разных поясах, пишущие `timestamp`,
создают данные, которые задним числом невозможно корректно сравнить. Поэтому по
умолчанию берут `timestamptz`, а `timestamp` — только когда пояс действительно
не имеет смысла (плановая дата, время работы магазина «с 9 до 18»).

**Числа.** `numeric` — точная десятичная арифметика, обязательна для денег.
`real` и `double precision` — двоичные с плавающей точкой, для денег
недопустимы: `0.1 + 0.2` там не равно `0.3`. Цена `numeric` — скорость: он
считается программно, а не процессором.

**Текст.** `text` и `varchar(n)` в PostgreSQL устроены одинаково и работают
одинаково быстро; `varchar(n)` лишь добавляет проверку длины. Ограничение «255
символов» из MySQL здесь смысла не имеет. Если ограничение длины — бизнес-правило,
его пишут явно.

**Идентификаторы.** `bigint` с `GENERATED ALWAYS AS IDENTITY` — современная
замена `serial`. `uuid` удобен, когда идентификатор нужно выдать до записи в
базу, но он в два раза шире и хуже ложится в индекс.

**Составные.** `jsonb` — для действительно неструктурированного, с индексом GIN
для поиска внутри. Массивы — когда элементы не являются самостоятельными
сущностями. Соблазн сложить в `jsonb` всё подряд надо гасить: это отказ от
типизации и от ограничений целостности.

> Источник: PostgreSQL 16 Documentation, «Data Types» —
> https://www.postgresql.org/docs/16/datatype.html

## 4. Что сейчас происходит на сервере

`pg_stat_activity` — первое, куда смотрят при разборе инцидента. Одна строка на
серверный процесс:

```sql
SELECT pid, state, wait_event_type, wait_event,
       now() - xact_start AS xact_age,
       left(query, 80) AS query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY xact_age DESC NULLS LAST;
```

Что читать:

- **`state`** — `active` (выполняет), `idle` (ждёт команду),
  **`idle in transaction`** (открыл транзакцию и забыл её закрыть).
- **`wait_event_type` и `wait_event`** — чего процесс ждёт: блокировки, ввода-вывода,
  клиента.
- **`xact_start`** — когда началась транзакция. Долгие транзакции — главный
  подозреваемый при распухании таблиц.

**`idle in transaction` — самая частая находка.** Такой сеанс держит снимок
данных, из-за чего `VACUUM` не может убрать старые версии строк **по всей базе**,
и таблицы растут, даже если в них ничего не пишут. Ограничивается настройкой
`idle_in_transaction_session_timeout`.

Аварийные средства, применять осознанно: `pg_cancel_backend(pid)` отменяет
текущий запрос, `pg_terminate_backend(pid)` обрывает соединение целиком.

Ещё два представления, которые пригодятся:

- **`pg_stat_user_tables`** — сколько последовательных и индексных сканов было по
  каждой таблице, сколько мёртвых строк накопилось. Таблица с большим
  `seq_scan` и нулевым `idx_scan` — кандидат на индекс.
- **`pg_stat_statements`** (расширение) — статистика по запросам за всё время:
  сколько раз выполнялся, сколько суммарно занял. Отвечает на вопрос «что грузит
  базу», на который `pg_stat_activity` ответить не может — он показывает только
  текущий момент.

> Источник: PostgreSQL 16 Documentation, «The Statistics Collector» —
> https://www.postgresql.org/docs/16/monitoring-stats.html

## 5. Размеры и место

```sql
SELECT relname,
       pg_size_pretty(pg_total_relation_size(relid)) AS total,
       pg_size_pretty(pg_relation_size(relid))       AS heap,
       n_dead_tup
FROM pg_stat_user_tables
ORDER BY pg_total_relation_size(relid) DESC
LIMIT 10;
```

`pg_total_relation_size` включает индексы и TOAST, `pg_relation_size` — только
сами данные. Разница между ними показывает, сколько занимают индексы: если они
весят больше таблицы, стоит проверить, все ли используются (`pg_stat_user_indexes`
покажет неиспользуемые).
