# PostgreSQL: индексы, селективность, покрывающие

> Конспект по документации PostgreSQL: главы «Indexes» и «Performance Tips».

Индексы — тема, где заученный ответ «добавить индекс» отличается от понимания
одним вопросом: «а почему он не используется?». Разбирать это надо на планах,
а не на определениях.

## Что нужно уметь после этого узла

- Выбрать тип индекса под задачу
- Определить порядок колонок в составном
- Назвать причины, по которым индекс не используется
- Объяснить селективность
- Добиться Index Only Scan
- Найти лишние индексы

---

## 1. Что такое индекс

Отдельная структура данных, хранящая **отсортированные значения колонок и
ссылки на строки**. Она позволяет найти нужные строки, не читая таблицу
целиком.

Из этого сразу следует цена: индекс — это **вторая копия данных**, которую
надо обновлять при каждой вставке, изменении и удалении. Ускоряя чтение, он
всегда замедляет запись.

---

## 2. Типы индексов

**B-tree** — по умолчанию и в 95% случаев то, что нужно. Умеет равенство,
диапазоны (`<`, `>`, `BETWEEN`), сортировку, префиксный поиск по строке
(`LIKE 'abc%'`), проверку на `NULL`.

**Hash** — только равенство. B-tree делает то же самое и умеет больше,
поэтому hash берут редко.

**GIN** — для значений, внутри которых много элементов: `jsonb`, массивы,
полнотекстовый поиск. Отвечает на вопрос «в каких строках встречается этот
элемент». Медленнее обновляется, чем B-tree.

**GiST** — геометрия, диапазоны, поиск ближайших соседей.

**BRIN** — для огромных таблиц, физически упорядоченных по колонке (обычно по
времени вставки). Хранит только минимум и максимум на блок, поэтому крошечный:
индекс на миллиард строк занимает мегабайты вместо гигабайтов. Работает
только при высокой корреляции между физическим порядком и значением —
на перемешанных данных бесполезен.

---

## 3. Селективность

**Селективность** — доля строк, которую отбирает условие. Чем она ниже, тем
полезнее индекс.

- `WHERE id = 12345` — одна строка из миллиона, селективность отличная;
- `WHERE status = 'active'` при 90% активных — индекс бесполезен, полный
  проход дешевле;
- `WHERE is_deleted = false` — то же самое.

**Почему индекс проигрывает на большой выборке.** Index Scan читает строки в
**случайном** порядке: нашёл ссылку в индексе — прыгнул в таблицу. Случайные
обращения к страницам дороже последовательного чтения. Начиная с некоторой
доли (единицы-десятки процентов) выгоднее прочитать таблицу подряд.

Планировщик это знает и считает по статистике. Поэтому Seq Scan в плане —
часто не проблема, а верное решение.

**Частичный индекс** решает проблему неселективной колонки:

```sql
CREATE INDEX orders_active_idx ON orders (created_at) WHERE status = 'active';
```

Если активных 0.1%, такой индекс в тысячу раз меньше обычного и дешевле в
поддержке. Условие индекса должно совпадать с условием запроса, иначе
планировщик его не применит.

---

## 4. Составные индексы

Порядок колонок решает всё. Правило: **колонки равенства первыми, диапазон —
последним.**

```sql
-- Для WHERE tenant_id = ? AND created_at BETWEEN ? AND ?
CREATE INDEX ON events (tenant_id, created_at);   -- верно
CREATE INDEX ON events (created_at, tenant_id);   -- плохо
```

Во втором варианте пришлось бы просматривать весь диапазон дат, отбирая
нужного арендатора уже после — то есть читать в сто раз больше.

**Левый префикс.** Индекс `(a, b, c)` используется для запросов по `a`, по
`(a, b)` и по `(a, b, c)`. Для запроса **только по `b`** он бесполезен —
как алфавитный указатель, по которому нельзя искать по второй букве.

Отсюда практический вывод: три индекса `(a)`, `(a, b)`, `(a, b, c)` —
избыточность. Первые два покрываются третьим.

---

## 5. Покрывающие индексы и Index Only Scan

Если все нужные запросу колонки есть в индексе, в таблицу можно не ходить
вовсе:

```sql
CREATE INDEX events_report_idx ON events (tenant_id, created_at) INCLUDE (kind);
```

`INCLUDE` добавляет колонки в индекс **без участия в сортировке** — они нужны
только для выдачи. В плане появится `Index Only Scan`, и разница бывает
двухпорядковой: сотни страниц против единиц.

**Условие, которое обязательно спросят:** Index Only Scan работает, только
если карта видимости говорит, что страница видна всем транзакциям, — а
заполняет её **VACUUM**. Без него в плане будет `Heap Fetches` с большим
числом, и весь выигрыш пропадёт.

---

## 6. Почему индекс не используется

Список, который стоит уметь перечислить целиком.

**1. Функция или выражение на колонке.**

```sql
WHERE date(created_at) = '2025-03-01'      -- индекс по created_at не поможет
WHERE created_at >= '2025-03-01'
  AND created_at <  '2025-03-02'            -- поможет
```

Альтернатива — индекс по выражению: `CREATE INDEX ON events (date(created_at))`.

**2. Несовпадение типов.** Сравнение `bigint` с текстовым литералом требует
приведения, и индекс может оказаться неприменим.

**3. Выборка слишком велика.** Разобрано выше — планировщик прав.

**4. Устаревшая статистика.** Планировщик считает, что строк вернётся много,
хотя их мало. Лечится `ANALYZE`.

**5. Таблица маленькая.** На сотне строк полный проход дешевле любого индекса,
и это нормально.

**6. `LIKE '%abc'`** — с ведущим подстановочным знаком B-tree бесполезен: он
упорядочен по началу строки. Нужен триграммный индекс (`pg_trgm`).

**7. `OR` по разным колонкам** часто мешает: планировщик может не суметь
объединить два индекса. Иногда помогает переписывание через `UNION`.

**8. Индекс не соответствует условию частичного индекса.**

## 7. Обслуживание

```sql
-- Использование индексов
SELECT indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes WHERE relname = 'events';

-- Размер таблицы и индексов
SELECT pg_size_pretty(pg_total_relation_size('events'));
```

`idx_scan = 0` за длительный период — кандидат на удаление: за такой индекс
платят все операции записи, а пользы нет. Исключение — индексы, поддерживающие
ограничения уникальности и внешние ключи.

**Создание без блокировки:**

```sql
CREATE INDEX CONCURRENTLY events_tenant_idx ON events (tenant_id);
```

Обычный `CREATE INDEX` блокирует запись в таблицу на всё время построения — на
боевой таблице это простой. `CONCURRENTLY` строится дольше и при сбое
оставляет невалидный индекс, который надо удалить и создать заново.

**Распухание индексов.** После массовых обновлений индекс, как и таблица,
содержит записи на мёртвые строки. Лечится `REINDEX CONCURRENTLY`. Симптом:
размер индекса заметно больше ожидаемого, а запросы по нему читают лишние
страницы.

---

## 8. Индексы и внешние ключи

PostgreSQL создаёт индекс автоматически для **первичного ключа** и для
ограничения `UNIQUE`, но **не создаёт** его для внешнего ключа.

Последствие, о котором забывают: удаление строки из родительской таблицы
требует проверить дочернюю, и без индекса это полный проход. На больших
таблицах удаление одной строки может занять минуты.

---

## 9. Что ещё спросят

- **Сколько индексов нормально.** Единицы. Каждый замедляет запись и занимает
  место; десяток индексов на таблице — обычно признак того, что их добавляли
  «на всякий случай», а не по планам.
- **Индекс по колонке с низкой кардинальностью.** Бесполезен сам по себе, но
  может быть полезен как часть составного или частичного.
- **`NULL` в индексе.** B-tree в PostgreSQL их хранит, поэтому `IS NULL`
  умеет использовать индекс — в отличие от некоторых других СУБД.
- **Индекс и сортировка.** `ORDER BY` по колонкам индекса может выполняться
  без отдельной сортировки: данные уже упорядочены. Это же убирает шаг
  сортировки перед оконными функциями.
