# dbt: модели, тесты, инкрементальность

> Конспект по документации dbt (docs.getdbt.com): «Models»,
> «Materializations», «Incremental models», «Tests», «Sources».

dbt встречается в вакансиях как инструмент слоя трансформаций и почти всегда
вместе с требованием «понимать моделирование». Спрашивают три вещи: чем dbt
принципиально отличается от скрипта с SQL, как устроена инкрементальная модель
и что происходит при `dbt run`.

## Что нужно уметь после этого узла

- Объяснить, что dbt делает с обычным `SELECT`
- Отличить model, source, seed и snapshot
- Выбрать материализацию под задачу и обосновать выбор
- Написать инкрементальную модель и объяснить `is_incremental()`
- Назвать встроенные тесты и сказать, что ловит каждый
- Объяснить, зачем `ref()` вместо имени таблицы

## 1. Что делает dbt

Модель dbt — это файл с одним `SELECT`:

```sql
-- models/marts/orders_daily.sql
SELECT
    date_trunc('day', created_at) AS day,
    count(*)                      AS orders,
    sum(amount)                   AS revenue
FROM {{ ref('stg_orders') }}
GROUP BY 1
```

dbt берёт этот `SELECT` и **оборачивает его в DDL**: `CREATE TABLE AS` или
`CREATE VIEW AS`, с нужным именем и в нужной схеме. Всё. Никакого своего
движка исполнения у dbt нет — вычисляет всё база, dbt только генерирует SQL и
выстраивает порядок.

Отсюда сразу следует то, что стоит уметь сказать вслух: **dbt — это T в ELT,
а не ETL-инструмент**. Он не забирает данные из источников и не грузит их в
хранилище; он преобразует то, что уже лежит внутри. За E и L отвечают Airflow,
Airbyte, коннекторы. Путать эти роли — типичная ошибка на собеседовании.

Второе важное свойство — **dbt не хранит состояния**. Модель описывает не
«что доложить», а «как должна выглядеть таблица». Прогон приводит хранилище к
этому описанию.

## 2. ref() и граф зависимостей

`{{ ref('stg_orders') }}` — не украшение. Это ключевая конструкция.

Когда модель ссылается на другую через `ref`, dbt:

1. **Подставляет полное имя** таблицы — схему и префикс окружения. В проде это
   `analytics.stg_orders`, в песочнице разработчика —
   `dbt_ivan.stg_orders`. Один и тот же код работает в обоих местах.
2. **Строит граф зависимостей** между моделями. Из него берётся порядок
   выполнения и возможность считать независимые модели параллельно.
3. **Умеет выбирать подграф**: `dbt run --select orders_daily+` пересчитает
   модель и всё, что от неё зависит.

Написать вместо `ref` имя таблицы строкой технически можно — и это ломает всё
перечисленное сразу. Порядок станет случайным, а окружения перестанут
разделяться.

**Source** — то же самое для внешних, не созданных dbt таблиц:

```yaml
sources:
  - name: raw
    tables:
      - name: orders
        freshness:
          warn_after: {count: 12, period: hour}
          error_after: {count: 24, period: hour}
```

```sql
SELECT * FROM {{ source('raw', 'orders') }}
```

Смысл тот же: явная граница проекта и точка, где проверяется свежесть
поступающих данных (`dbt source freshness`).

## 3. Материализации

Материализация — это способ, которым модель превращается в объект базы.
Задаётся в конфиге модели или в `dbt_project.yml`.

| Материализация | Что создаётся | Когда уместна |
|---|---|---|
| `view` | представление | лёгкие преобразования, данные нужны свежими всегда |
| `table` | таблица, полностью перезаписывается | тяжёлые агрегаты, читаются часто |
| `incremental` | таблица, дополняется порциями | большие факты, полный пересчёт слишком дорог |
| `ephemeral` | ничего; код встраивается в потребителя как CTE | промежуточный шаг, не нужный снаружи |

Правило выбора простое: начинать с `view`, переходить на `table`, когда
чтение стало медленным, и на `incremental` — когда полный пересчёт стал
дорогим. Идти сразу в `incremental` не стоит: он сложнее и добавляет целый
класс ошибок, разобранных ниже.

`ephemeral` не создаёт объекта вовсе, поэтому его нельзя посмотреть в базе и
неудобно отлаживать — это плата за отсутствие лишней сущности.

## 4. Инкрементальные модели

Модель, которая при первом запуске строится целиком, а дальше только
дополняется:

```sql
{{ config(materialized='incremental', unique_key='order_id') }}

SELECT *
FROM {{ source('raw', 'orders') }}

{% if is_incremental() %}
  -- Этот блок попадает в SQL только при дозаписи, не при первой сборке
  WHERE updated_at > (SELECT max(updated_at) FROM {{ this }})
{% endif %}
```

Три конструкции, которые надо понимать:

- **`is_incremental()`** истинно, когда таблица уже существует, прогон не
  полный (`--full-refresh`) и материализация инкрементальная. Именно поэтому
  фильтр обёрнут в условие: при первой сборке ограничивать нечего.
- **`{{ this }}`** — сама строящаяся таблица. Через неё берут «докуда уже
  дошли».
- **`unique_key`** — ключ, по которому dbt обновит уже существующие строки
  вместо вставки дубликата. Без него инкрементальная модель умеет только
  добавлять, и любая перезагрузка порождает задвоение.

**Как это исполняется.** dbt собирает результат `SELECT` во временную таблицу,
затем выполняет `MERGE` (или `DELETE` + `INSERT`, в зависимости от базы и
стратегии) в целевую. Стратегия задаётся `incremental_strategy`: `merge`,
`append`, `delete+insert`, `insert_overwrite`.

**Где обычно ломается:**

1. **Опоздавшие данные.** Фильтр `updated_at > max(updated_at)` пропустит
   запись, пришедшую с задержкой. Лечится окном перекрытия: брать не «после
   максимума», а «после максимума минус три дня» — вместе с `unique_key`,
   который снимет дубликаты.
2. **Нет `unique_key` при повторном запуске.** Прогон дважды за один период
   удваивает строки. Это та же идемпотентность, что и в оркестрации.
3. **Изменилась логика модели.** Инкрементальная таблица хранит строки,
   посчитанные СТАРЫМ кодом. Новая логика применится только к новым данным,
   и таблица станет смесью двух версий. Лечение — `dbt run --full-refresh`
   после смысловых изменений.
4. **Источник обновляет строки задним числом**, а фильтр смотрит на
   `created_at`, а не на `updated_at`. Изменения просто не приедут.

## 5. Тесты

Тест в dbt — это `SELECT`, который **возвращает плохие строки**. Пусто —
тест прошёл. Идея простая и её удобно назвать на собеседовании.

Четыре встроенных теста:

```yaml
models:
  - name: orders_daily
    columns:
      - name: day
        tests: [unique, not_null]
      - name: status
        tests:
          - accepted_values: {values: ['new', 'paid', 'shipped']}
      - name: customer_id
        tests:
          - relationships: {to: ref('customers'), field: id}
```

- `unique` — дубликаты ключа, самая частая порча витрины;
- `not_null` — пропуски там, где их быть не может;
- `accepted_values` — значение вне допустимого набора, обычно признак
  изменения в источнике;
- `relationships` — ссылочная целостность: заказ на несуществующего клиента.

Своих тестов бывает два вида: **singular** (просто файл с `SELECT` в
`tests/`) и **generic** (параметризуемый тест, который можно навешивать на
любую колонку). Плюс пакет `dbt-utils` с готовыми проверками вроде
`expression_is_true` и `recency`.

Важное про строгость: у теста есть `severity` — `error` останавливает прогон,
`warn` только сообщает. И `--store-failures`, складывающий плохие строки в
таблицу: без этого «тест упал» превращается в загадку.

## 6. Что происходит при `dbt run`

Порядок, который стоит уметь пересказать:

1. dbt читает проект и **компилирует** модели: разворачивает Jinja, `ref` и
   `source` в настоящие имена. Результат лежит в `target/compiled` — туда и
   надо смотреть при отладке.
2. Строит **DAG** по зависимостям из `ref`.
3. Выполняет модели в топологическом порядке, независимые — параллельно, число
   потоков задаёт `threads`.
4. Пишет **артефакты** в `target/`: `manifest.json` (полный граф и метаданные)
   и `run_results.json` (что и сколько выполнялось).

Полезные команды: `dbt build` — прогон моделей вместе с тестами в правильном
порядке; `dbt docs generate` — документация с интерактивным графом;
`dbt run --select tag:daily` — выборочный прогон.

## 7. Snapshot и seed

**Snapshot** — механизм для медленно меняющихся измерений типа 2 (см.
`dwh.scd`). dbt сам следит за изменениями строк источника и ведёт историю с
`dbt_valid_from` и `dbt_valid_to`:

```sql
{% snapshot customers_snapshot %}
{{ config(unique_key='id', strategy='check', check_cols=['email', 'plan']) }}
SELECT * FROM {{ source('raw', 'customers') }}
{% endsnapshot %}
```

Стратегии две: `timestamp` (доверять колонке времени изменения) и `check`
(сравнивать перечисленные колонки). Первая дешевле, вторая надёжнее, когда
источник времени изменения не ведёт.

**Seed** — небольшой CSV в репозитории, загружаемый в таблицу командой
`dbt seed`. Справочники, маппинги, списки исключений. Для данных, а не для
справочников, это не годится: CSV в git — это версионируемый файл, а не
хранилище.
