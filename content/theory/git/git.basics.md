# Git: ветки, история, разрешение конфликтов

> Конспект по официальной книге Pro Git: главы «Git Basics», «Git Branching»,
> «Git Tools».

Git не спрашивают отдельной темой — его проверяют между делом, по тому, как
человек говорит о работе. Умение внятно ответить «что ты сделаешь, если
запушил в мастер лишнее» стоит больше, чем знание сорока команд.

## Что нужно уметь после этого узла

- Объяснить, что такое коммит, ветка и HEAD
- Восстановить работу после неудачной команды
- Выбрать между merge и rebase
- Разрешить конфликт, понимая маркеры
- Отменить изменения тремя способами
- Написать полезное сообщение коммита

---

## 1. Из чего состоит Git

**Коммит** — снимок всего дерева файлов плюс ссылка на родителя. Не «набор
изменений», а именно снимок: разницу Git вычисляет при показе. У коммита есть
идентификатор — хеш содержимого, поэтому изменить старый коммит, не поменяв
все последующие, невозможно.

**Ветка** — просто указатель на коммит. Файл в двадцать байт. Отсюда правило:
ветки в Git дёшевы, и заводить их надо свободно — под задачу, под эксперимент,
под «а что если».

**HEAD** — указатель на то, где ты сейчас. Обычно указывает на ветку, а та —
на коммит.

**Три области**, между которыми ходят файлы:

```
рабочий каталог  →  индекс (staging)  →  репозиторий
     правки           git add            git commit
```

Индекс существует, чтобы собрать коммит выборочно: сделал пять правок, а
закоммитил две связанные. `git add -p` даёт добавлять по кускам внутри файла —
это то, чем отличается аккуратная история от свалки.

## 2. Ежедневный набор

```bash
git status                 # что изменено и что в индексе
git diff                   # правки, ещё не добавленные в индекс
git diff --staged          # что уйдёт в коммит
git log --oneline --graph  # история компактно, с ветвлением
git switch -c feature/x    # создать ветку и перейти
git switch main            # вернуться
```

`git switch` и `git restore` появились как замена перегруженному `git
checkout`, который делал три разные вещи. Новые команды понятнее, старая
работает по-прежнему.

---

## 3. merge против rebase

Обе команды переносят работу из одной ветки в другую. Разница — в том, что
остаётся в истории.

**Merge** создаёт коммит слияния с двумя родителями. История сохраняется как
было: видно, что ветка существовала и когда влилась.

**Rebase** переписывает коммиты ветки поверх нового основания. История
получается линейной, будто работа велась последовательно. Но коммиты
**новые** — с другими хешами.

Правило, которое надо знать наизусть: **не переписывай историю, которую уже
видели другие.** Rebase опубликованной ветки заставит всех, кто её забрал,
разбираться с расхождением. Своя ветка до пул-реквеста — переписывай сколько
угодно; общая ветка — только merge.

Типичный рабочий приём: перед отправкой пул-реквеста сделать `git rebase main`,
чтобы ветка ложилась поверх свежего основания и конфликты разрешались у тебя,
а не у ревьюера.

---

## 4. Конфликты

Конфликт возникает, когда две ветки поменяли **одни и те же строки**. Git не
угадывает, чей вариант верен, и оставляет маркеры:

```
<<<<<<< HEAD
цена = сумма * 1.2
=======
цена = сумма * 1.18
>>>>>>> feature/vat
```

Сверху — то, что в текущей ветке (куда вливаешь), снизу — то, что приходит.
Разрешение — это не «выбрать одну из половин», а **написать правильный
итоговый код**, после чего убрать маркеры и сделать `git add`.

Полезное:

```bash
git status              # список конфликтующих файлов
git diff                # что именно разошлось
git merge --abort       # передумать и вернуться как было
git checkout --ours f   # взять свою версию файла целиком
git checkout --theirs f # взять приходящую
```

Главный способ уменьшить число конфликтов — не длинные ветки. Ветка, живущая
три недели, конфликтует со всем; ветка на два дня — почти ни с чем.

## 5. Отмена изменений

Три разные команды, которые путают чаще всего.

**`git restore <файл>`** — выбросить правки в рабочем каталоге. Безвозвратно,
Git их не видел.

**`git reset`** — двигает указатель ветки назад.

- `--soft` — коммиты отменены, изменения остаются в индексе;
- `--mixed` (по умолчанию) — изменения остаются в рабочем каталоге;
- `--hard` — **изменения уничтожаются**.

Reset переписывает историю, поэтому в общей ветке он опасен.

**`git revert <коммит>`** — создаёт НОВЫЙ коммит, отменяющий указанный.
История не переписывается, все могут спокойно забрать изменения. **Это
единственный правильный способ откатить что-то в общей ветке.**

Ответ на вопрос «запушил в мастер лишнее»: `git revert`. Ответ «сделал бы
reset --hard и force push» — красный флаг на собеседовании.

---

## 6. Как ничего не потерять

**`git reflog`** — журнал всех перемещений HEAD за последние недели, включая
то, что не видно в `git log`. Через него достаётся работа после неудачного
reset, потерянная ветка, коммиты после rebase.

```bash
git reflog                     # найти хеш нужного состояния
git reset --hard <хеш>         # вернуться к нему
```

Практически это значит: **закоммиченное потерять почти невозможно**. Опасны
только незакоммиченные правки — их не защищает ничто. Отсюда привычка
коммитить часто, а причёсывать историю потом.

**`git stash`** — отложить незавершённую работу, чтобы переключиться:

```bash
git stash push -m "начал рефакторинг"
git switch main
git stash pop
```

## 7. Сообщения коммитов

Сообщение пишется для того, кто через год будет выяснять, **почему** так
сделано. Что происходит, видно из диффа; почему — только из сообщения.

Полезная форма:

```
fix(loader): не терять строки с NULL в ключе соединения

INNER JOIN отбрасывал заказы без клиента, из-за чего суточная выручка
была занижена примерно на 2%. Заменён на LEFT JOIN с явной обработкой
несопоставленных строк.
```

Первая строка — что сделано, коротко и в повелительном наклонении. Дальше
пустая строка и объяснение причины.

**Conventional Commits** (`feat`, `fix`, `docs`, `refactor`, `test`, `chore`)
— соглашение о префиксе. Оно нужно не ради красоты: по нему автоматически
собирается список изменений и определяется, менять ли минорную или мажорную
версию. В этом репозитории соглашение проверяется хуком commitizen.

## 8. Работа с удалёнными репозиториями

```bash
git fetch            # забрать изменения, НЕ трогая рабочую ветку
git pull             # fetch + merge (или rebase при --rebase)
git push             # отправить
git push --force-with-lease  # переписать удалённую ветку безопасно
```

`--force-with-lease` вместо `--force` — важная деталь: он откажется затирать
чужие изменения, появившиеся после твоего последнего fetch. Обычный `--force`
затрёт молча.

`git fetch` безопасен всегда и полезен как привычка: сначала посмотреть, что
пришло, потом решать, сливать или перебазировать.

## 9. Что ещё спросят

- **`.gitignore`.** Не должно попадать в репозиторий: секреты, виртуальные
  окружения, артефакты сборки, большие данные. Уже закоммиченный файл
  .gitignore не убирает — нужен `git rm --cached`.
- **Секрет попал в историю.** Добавления в .gitignore недостаточно: он
  остаётся в коммитах. Секрет нужно **отозвать и заменить**, а историю чистить
  отдельным инструментом. Первое действие — сменить пароль, а не переписать
  историю.
- **`git cherry-pick`** — перенести один коммит из другой ветки.
- **`git bisect`** — бинарный поиск коммита, сломавшего поведение. Тот же
  приём, что и поиск дня, с которого поехали данные.
- **Squash при слиянии** — схлопнуть ветку в один коммит. Делает историю
  главной ветки читаемой ценой потери промежуточных шагов.
