# Docker: образы, контейнеры, тома, compose

> Конспект по документации Docker: «Get started», «Build», «Storage»,
> «Networking», «Compose».

У инженера данных Docker встречается всюду: в нём приезжают Airflow, Spark,
ClickHouse, в нём же гоняются тесты. Спрашивают не команды, а понимание —
почему данные пропали после перезапуска и почему контейнер не видит соседа.

## Что нужно уметь после этого узла

- Объяснить разницу образа и контейнера
- Прочитать Dockerfile и найти, что ломает кеш
- Выбрать между томом и монтированием каталога
- Починить связь между контейнерами
- Найти причину падения по логам и коду выхода
- Объяснить отличие от виртуальной машины

---

## 1. Образ и контейнер

**Образ** — неизменяемый шаблон: файловая система плюс метаданные о том, что
запускать. **Контейнер** — запущенный экземпляр образа с добавленным сверху
тонким **записываемым слоем**.

Отсюда главное практическое следствие: **всё, что контейнер записал в свою
файловую систему, исчезает вместе с ним**. База данных в контейнере без тома
теряет данные при `docker rm`. Это не баг, а устройство.

Образ состоит из **слоёв** — по слою на инструкцию Dockerfile. Слои общие
между образами: если десять образов собраны на одном базовом, он лежит на
диске один раз.

---

## 2. Чем это отличается от виртуальной машины

Виртуальная машина эмулирует оборудование и несёт **собственное ядро** и
полную операционную систему. Контейнер использует **ядро хоста**, а
изолируется механизмами самого ядра: пространства имён (namespaces) разделяют
что процесс видит, контрольные группы (cgroups) ограничивают сколько он
потребляет.

Практические следствия:

- контейнер стартует за доли секунды, ВМ — за десятки;
- контейнер весит десятки мегабайт, а не гигабайты;
- **на Linux-хосте нельзя запустить контейнер с другим ядром** — отсюда
  прослойка виртуализации на Windows и macOS;
- изоляция слабее, чем у ВМ: root в контейнере при небрежной настройке — это
  почти root на хосте.

## 3. Dockerfile и кеш слоёв

```dockerfile
FROM python:3.12-slim

WORKDIR /app

# Сначала зависимости — они меняются редко
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Потом код — он меняется на каждый коммит
COPY . .

CMD ["python", "-m", "app"]
```

Docker кеширует результат каждой инструкции. Если инструкция и её вход не
изменились, слой берётся из кеша. **Изменение любого слоя обесценивает все
последующие.**

Отсюда единственное правило, которое даёт основной выигрыш: **сначала то, что
меняется редко, потом то, что меняется часто.** Скопировать код до установки
зависимостей — значит переустанавливать их на каждую правку одной строки.

Другие вещи, которые стоит знать:

- **`.dockerignore`** — исключает из контекста сборки то, что не нужно:
  `.git`, виртуальные окружения, данные. Без него в демон отправляются
  гигабайты, и сборка «висит» на этапе передачи контекста.
- **`RUN apt-get update && apt-get install`** одной инструкцией. Раздельно они
  дают устаревший кеш update при свежем install.
- **Многоступенчатая сборка** — компилировать в одном образе, а в итоговый
  копировать только результат:

```dockerfile
FROM golang:1.22 AS build
RUN go build -o /app

FROM gcr.io/distroless/base
COPY --from=build /app /app
```

Итоговый образ не содержит ни компилятора, ни исходников — меньше размер и
меньше поверхность атаки.

- **`CMD` против `ENTRYPOINT`.** ENTRYPOINT задаёт саму программу, CMD —
  аргументы по умолчанию, которые легко переопределить при запуске.
- **Не запускать от root.** `USER appuser` — одна строка, снимающая целый
  класс проблем.

## 4. Данные: тома и монтирование

Три способа дать контейнеру постоянные данные:

**Том (volume)** — хранилище, которым управляет Docker:

```bash
docker volume create pgdata
docker run -v pgdata:/var/lib/postgresql/data postgres:16
```

Живёт независимо от контейнера, переживает пересоздание, переносится между
контейнерами. **Это правильный выбор для данных баз.**

**Монтирование каталога (bind mount)** — каталог хоста внутрь контейнера:

```bash
docker run -v $(pwd)/src:/app/src myimage
```

Правильный выбор для разработки: правка кода видна сразу, без пересборки.
Зависит от путей на хосте, поэтому в проде используется редко.

**tmpfs** — в оперативной памяти, исчезает при остановке. Для временных
файлов и секретов.

Частая ошибка: перезапустили `docker compose down -v` и удивились пропаже
данных. Флаг `-v` удаляет тома — именно то, что просили.

## 5. Сеть

Контейнеры одной сети видят друг друга **по имени сервиса**, а не по
`localhost`.

```yaml
services:
  api:
    environment:
      # Верно: имя сервиса
      DATABASE_URL: postgresql://user:pass@postgres:5432/db
  postgres:
    image: postgres:16
```

Это ошибка номер один у начинающих: `localhost` внутри контейнера означает сам
этот контейнер, а не хост и не соседа.

**Проброс портов** `-p 8080:80` связывает порт хоста с портом контейнера:
слева хост, справа контейнер. Без проброса сервис доступен только внутри сети
Docker.

Обратная задача — достучаться из контейнера до сервиса **на хосте** — решается
именем `host.docker.internal` (на Linux требует явного `--add-host`).

## 6. Compose

Compose описывает набор сервисов одним файлом:

```yaml
services:
  postgres:
    image: pgvector/pgvector:pg16
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 10

  api:
    build: .
    depends_on:
      postgres:
        condition: service_healthy
    ports:
      - "127.0.0.1:8000:8000"

volumes:
  pgdata:
```

Две детали, которые отличают рабочий файл от учебного:

**`depends_on` без `condition` ждёт только СТАРТА контейнера, а не готовности
сервиса.** Postgres стартует за секунду, а принимать соединения начинает
позже — и приложение падает на старте. Лечится проверкой здоровья и
`condition: service_healthy`.

**Публикация порта как `127.0.0.1:8000:8000`, а не `8000:8000`.** Второй
вариант открывает порт наружу, во все сети машины, — и на ноутбуке в кафе это
открытая база.

Полезно ещё:

- **профили** (`profiles: [analytics]`) — не поднимать всё сразу;
- **ограничения памяти** — иначе один контейнер съедает всю машину;
- **`docker compose up --build`** — без `--build` правка кода не попадёт в
  образ, и вы будете отлаживать вчерашнюю версию.

## 7. Диагностика

```bash
docker ps -a                 # все контейнеры, включая упавшие
docker logs -f <имя>         # логи, следить
docker exec -it <имя> bash   # зайти внутрь работающего
docker inspect <имя>         # полная конфигурация
docker stats                 # потребление ресурсов
docker compose logs api      # логи одного сервиса
```

**Коды выхода** стоит знать:

- `0` — штатное завершение;
- `1` — ошибка приложения, смотреть логи;
- `125` — не смог запуститься сам docker (неверные аргументы);
- `126` — команда найдена, но не исполняема;
- `127` — команда не найдена в образе;
- `137` — **убит по нехватке памяти** (OOM) либо `kill -9`;
- `143` — остановлен штатно (SIGTERM).

`137` — самый информативный из них: он означает, что контейнеру не хватило
памяти, а не что программа сломалась. Лечится увеличением лимита или
уменьшением аппетита программы.

Контейнер, который сразу завершается: **основной процесс закончил работу**.
Docker живёт ровно столько, сколько живёт процесс с PID 1. Команда вроде
`bash` без `-it` завершится немедленно.

## 8. Что ещё спросят

- **Почему образ такой большой.** Кеш пакетного менеджера, исходники,
  оставшиеся после сборки, отсутствие `.dockerignore`, `slim`/`alpine` вместо
  полного базового образа.
- **Alpine.** Меньше, но использует musl вместо glibc — часть пакетов Python
  собирается заново или ведёт себя иначе. Экономия иногда стоит дороже.
- **Тег `latest`** — не «последняя версия», а просто тег по умолчанию. В
  проде и в CI образы фиксируют версией, иначе сборка перестаёт быть
  воспроизводимой.
- **Секреты в образе.** Всё, что попало в слой, остаётся в нём навсегда, даже
  если удалено следующей инструкцией. Секреты передаются переменными
  окружения или механизмом секретов, а не `COPY`.
- **docker.sock внутрь контейнера.** Даёт контейнеру полный контроль над
  хостом. В этом проекте песочница ката его не получает намеренно, и на это
  есть тест.
