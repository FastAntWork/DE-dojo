# Airflow: DAG, операторы, расписание

> Конспект по документации Apache Airflow: «Core Concepts», «DAG Runs»,
> «Tasks», «XComs», «Best Practices».

Airflow — самый частый оркестратор в вакансиях DE. Спрашивают редко про
синтаксис и почти всегда про поведение: что произойдёт при перезапуске, чем
логическая дата отличается от фактической, куда девать данные между задачами.

## Что нужно уметь после этого узла

- Объяснить роль Airflow и что он **не** делает
- Пересказать путь от файла DAG до запущенной задачи
- Отличить логическую дату интервала от времени запуска
- Выбрать способ передачи данных между задачами
- Прочитать состояние задачи и понять, куда смотреть
- Назвать типовые ошибки в коде DAG

---

## 1. Что такое Airflow и чем он не является

Airflow **запускает задачи в нужном порядке в нужное время и следит за
результатом**. Он не обрабатывает данные.

Это главная мысль темы, и её стоит уметь произнести отдельно. Задача Airflow
должна отправить работу туда, где для неё есть ресурсы: запрос в хранилище,
джобу в Spark, прогон dbt, вызов API. Если задача сама читает гигабайты в
память процесса-исполнителя, оркестратор превращается в место обработки
данных — и падает от нагрузки, для которой не предназначен.

Типовая формулировка на собеседовании: **Airflow дирижёр, а не оркестр**.

## 2. DAG

DAG — направленный ациклический граф задач. Описывается кодом на Python:

```python
from airflow.decorators import dag, task
import pendulum


@dag(
    schedule="0 3 * * *",
    start_date=pendulum.datetime(2025, 1, 1, tz="UTC"),
    catchup=False,
    max_active_runs=1,
    default_args={"retries": 3, "retry_delay": pendulum.duration(minutes=5)},
)
def daily_orders():
    @task
    def extract(logical_date=None) -> str:
        # Возвращаем ПУТЬ, а не данные
        return f"s3://raw/orders/{logical_date:%Y-%m-%d}/"

    @task
    def load(path: str) -> None:
        ...

    load(extract())


daily_orders()
```

Ациклический — потому что цикл означал бы задачу, ждущую саму себя.
Зависимости задаются либо передачей результата (как выше), либо явно:
`a >> b >> c`.

**Идентификаторы стабильны.** `dag_id` и `task_id` — ключи, по которым живёт
история запусков. Переименование задачи означает потерю её истории и
появление новой сущности с нуля.

## 3. Что происходит от файла до запуска

Порядок, который просят пересказать:

1. **Парсер DAG** периодически читает файлы из каталога DAG и исполняет их как
   Python. Не запускает задачи — именно исполняет файл, чтобы получить объект
   графа.
2. **Планировщик** решает, какие интервалы уже пора запускать, и создаёт
   **DAG run** — конкретный прогон за конкретный интервал.
3. Задачи прогона, у которых закрыты зависимости, переводятся в очередь
   (`queued`).
4. **Исполнитель** (Local, Celery, Kubernetes) забирает задачи и запускает их
   на воркерах.
5. Состояния и логи пишутся в базу метаданных, интерфейс читает их оттуда.

Из первого пункта следует важнейшее практическое правило: **файл DAG
исполняется целиком много раз в минуту**. Всё, что написано на верхнем уровне
модуля, выполняется при каждом разборе.

```python
# ПЛОХО: выполняется при каждом разборе файла, десятки раз в минуту
df = pandas.read_sql("SELECT * FROM huge_table", conn)


@task
def use_it():
    ...
```

Тяжёлые импорты, обращения к базе, запросы к API на верхнем уровне — самая
частая причина того, что «Airflow тормозит». Всё это должно жить **внутри**
функций задач.

## 4. Расписание и логическая дата

Самая путаная часть темы и любимый вопрос.

У прогона есть **интервал данных**, за который он отвечает, и **фактическое
время запуска**. Прогон за сутки 1 марта стартует, когда эти сутки
закончились, — то есть 2 марта. Это не задержка и не ошибка: раньше данных за
1 марта просто не существует.

- `logical_date` (прежнее имя — `execution_date`) — начало интервала,
  за который отвечает прогон;
- `data_interval_start` / `data_interval_end` — его границы явно;
- фактическое время старта — отдельная величина, в логике задач ей делать
  нечего.

**Правило: задача должна брать границы обрабатываемого периода из контекста,
а не из `datetime.now()`.** Иначе повторный запуск за прошлый день обработает
сегодняшние данные, а backfill станет бессмысленным. Это же условие
идемпотентности — см. `airflow.idempotency`.

**`catchup`** решает, что делать с интервалами между `start_date` и текущим
моментом. `catchup=True` запустит их все — включая сотни исторических, если
`start_date` в прошлом году. Это регулярно роняет свежепоставленный Airflow,
поэтому по умолчанию в проектах ставят `False` и запускают историю осознанно.

**`max_active_runs=1`** не даёт прогонам одного DAG идти внахлёст — важно,
когда они пишут в одну таблицу.

Кроме cron есть расписание **по данным**: DAG запускается, когда обновился
объявленный набор данных (`Dataset`/`Asset`), а не по часам. Это убирает
хрупкую конструкцию «поставим второй DAG на час позже и понадеемся».

## 5. Операторы и задачи

**Оператор** — шаблон задачи. `PythonOperator`, `BashOperator`,
`SQLExecuteQueryOperator`, операторы провайдеров (Spark, dbt, облака).
**Задача** — экземпляр оператора в конкретном DAG. **Task instance** — эта
задача в конкретном прогоне; именно у неё есть состояние и логи.

**Сенсор** — задача, которая ждёт события: появления файла, готовности
партиции, ответа API. Важная деталь: сенсор в обычном режиме **занимает слот
воркера всё время ожидания**. Десяток сенсоров, ждущих по шесть часов,
блокируют пул. Лечение — `mode="reschedule"` (сенсор освобождает слот между
проверками) или отложенные операторы (deferrable), уходящие в триггерер.

**TaskFlow API** — декораторы `@dag` и `@task`, показанные выше. Это
современный способ: зависимости выводятся из передачи значений, а не
описываются отдельно.

## 6. Передача данных между задачами

Задачи выполняются **в разных процессах, а часто и на разных машинах**.
Общей памяти у них нет.

**XCom** — механизм обмена маленькими значениями через базу метаданных. Он
подходит для путей, идентификаторов, количеств. Он **не подходит для данных**:
всё, что уходит в XCom, сериализуется и складывается в служебную базу, и
датафрейм там означает раздутую метабазу и медленный интерфейс.

Правильный приём: **передавать ссылку, а не содержимое**. Задача пишет
результат в S3 или в таблицу и возвращает путь. Следующая задача читает по
пути. Ровно это делает пример из раздела 2.

Отсюда же вытекает запрет на **состояние в памяти между задачами**: глобальные
переменные, открытые соединения, накопленные списки. Каждая задача обязана
быть самодостаточной.

## 7. Состояния задач и где искать причину

| Состояние | Что означает | Куда смотреть |
|---|---|---|
| `queued` | задача в очереди, воркер не взял | свободные слоты, пулы, исполнитель |
| `running` | выполняется | логи задачи |
| `up_for_retry` | упала, будет перезапущена | логи предыдущей попытки |
| `failed` | попытки кончились | логи последней попытки |
| `upstream_failed` | упала зависимость, задача не запускалась | причина у предка |
| `skipped` | пропущена ветвлением или правилом запуска | логика ветвления |
| `up_for_reschedule` | сенсор ждёт, слот освобождён | условие ожидания |

Две частые ловушки:

- **Задача долго `queued`.** Дело не в самой задаче: не хватает слотов в пуле,
  или упёрлись в `parallelism`, или исполнитель не справляется.
- **`upstream_failed`.** Смотреть логи этой задачи бесполезно, их нет. Причина
  выше по графу.

**Правила запуска** (`trigger_rule`) определяют, при каком состоянии
предков задача выполняется. По умолчанию `all_success`. Значения вроде
`all_done` и `one_failed` нужны для задач уборки и оповещения, которые обязаны
отработать даже при падении.

## 8. Типовые ошибки

1. **Работа на верхнем уровне файла** — разобрано выше, самая частая.
2. **`datetime.now()` в логике** вместо контекстных дат — ломает
   воспроизводимость и backfill.
3. **Обработка данных в самой задаче** вместо отправки работы в хранилище или
   Spark.
4. **Большие объекты в XCom.**
5. **Отсутствие `retries`** там, где ошибка сетевая и проходит сама.
6. **Секреты в коде DAG** вместо Connections и Variables (а лучше внешнего
   хранилища секретов).
7. **Задачи-монолиты** на час работы: падение в конце означает повтор всего.
   Дробить стоит по границам, где результат уже где-то сохранён.
