# MPP и Greenplum: дистрибуция, перекос, партиционирование

> Конспект по документации Greenplum: «Distribution and Skew», «Partitioning
> Large Tables», «Table Storage Models».

Greenplum встречается в российских вакансиях DE заметно чаще, чем в мировых:
он лежит в основе многих корпоративных хранилищ. Спрашивают почти всегда одно
и то же — ключ дистрибуции и перекос.

## Что нужно уметь после этого узла

- Объяснить устройство MPP и следствия для запросов
- Выбрать ключ дистрибуции и обосновать выбор
- Отличить перекос данных от перекоса вычислений
- Прочитать Motion в плане запроса
- Отличить дистрибуцию от партиционирования
- Выбрать ориентацию хранения и сжатие

## 1. Что такое MPP

**Massively Parallel Processing** — архитектура, где данные разложены по
множеству независимых узлов, и каждый обрабатывает свою часть параллельно.

Greenplum устроен как **координатор** плюс **сегменты**. Координатор принимает
запрос, строит план, раздаёт его сегментам и собирает результат. Сегменты —
это по сути отдельные экземпляры PostgreSQL, каждый со своей частью данных и
своим диском.

Отсюда главное следствие: **производительность определяется самым медленным
сегментом**. Если на одном из шестидесяти сегментов лежит десятая часть всех
данных, то запрос будет идти столько, сколько нужно этому сегменту, а
остальные пятьдесят девять будут ждать. Ускорить это добавлением сегментов
нельзя.

Второе следствие: **данные, лежащие на разных сегментах, приходится
перемещать**, когда операция требует их вместе. Это движение называется
**Motion** и стоит дорого — ровно как shuffle в Spark.

Третье: Greenplum совместим с PostgreSQL по синтаксису, но это **не**
PostgreSQL по поведению. Запрос, отлично работающий на одиночном сервере,
может быть катастрофическим на MPP, и наоборот.

## 2. Дистрибуция

Каждая таблица имеет **ключ дистрибуции** — колонки, по хешу которых строка
попадает на конкретный сегмент.

```sql
CREATE TABLE orders (...)
DISTRIBUTED BY (order_id);
```

Варианты:

- **`DISTRIBUTED BY (колонки)`** — по хешу. Основной способ.
- **`DISTRIBUTED RANDOMLY`** — равномерно, но случайно. Соединение по любому
  ключу потребует перемещения. Годится для таблиц, которые ни с чем не
  соединяются.
- **`DISTRIBUTED REPLICATED`** — копия таблицы на каждом сегменте. Для
  маленьких справочников: соединение с ними становится локальным. Аналог
  broadcast join в Spark.

**Как выбирать ключ.** Три требования, и они конфликтуют:

1. **Высокая кардинальность и равномерность** — иначе перекос.
2. **Совпадение с ключом соединения** — тогда соединение локальное, без
   Motion.
3. **Отсутствие в частых фильтрах равенства** — иначе запрос по одному
   значению ключа уйдёт на один сегмент, и весь параллелизм пропадёт.

Практика: для таблицы фактов берут суррогатный или естественный ключ высокой
кардинальности, по которому чаще всего идут соединения. **Дата — плохой ключ
дистрибуции**: запросы фильтруют по ней, и суточный отчёт исполнится на одном
сегменте. Дата — это ключ **партиционирования**, а не дистрибуции.

Проверка перекоса в одну команду:

```sql
SELECT gp_segment_id, count(*)
FROM orders
GROUP BY 1
ORDER BY 2 DESC;
```

Разброс в разы означает плохой ключ.

## 3. Перекос данных и перекос вычислений

Различие, которое любят спрашивать.

**Перекос данных (data skew)** — строки распределены неравномерно **при
хранении**. Виден запросом выше, существует постоянно, лечится сменой ключа
дистрибуции.

**Перекос вычислений (computation skew)** — данные лежат ровно, но
**конкретный запрос** сгружает работу на один сегмент. Возникает при
группировке или соединении по колонке с сильно неравномерным распределением
значений: после перераспределения все строки популярного значения оказываются
на одном сегменте.

Перекос вычислений не виден в покое — он проявляется только на конкретном
запросе. Именно поэтому «таблица распределена равномерно» не означает
«запросы будут быстрыми».

Лечится он иначе: изменением самого запроса (предагрегация, отделение
популярных значений), а не сменой ключа дистрибуции.

## 4. Motion в плане запроса

`EXPLAIN` в Greenplum показывает узлы движения данных. Их три вида, и по ним
читается стоимость запроса.

- **Redistribute Motion** — строки перераспределяются по новому ключу.
  Возникает, когда соединение идёт не по ключу дистрибуции. Дорого:
  перемещается вся таблица.
- **Broadcast Motion** — таблица целиком рассылается на все сегменты.
  Разумно для маленькой стороны, разрушительно для большой.
- **Gather Motion** — результат собирается на координаторе. Есть почти в
  каждом плане в самом верху; беда, если под ним огромное число строк, — тогда
  координатор становится узким местом.

Идеальное соединение — **без Motion вовсе**: обе таблицы распределены по
ключу соединения, и каждый сегмент соединяет своё со своим локально. Именно
ради этого ключ дистрибуции подбирают под типовые соединения.

```sql
-- Обе распределены по customer_id → соединение локальное
CREATE TABLE orders (...) DISTRIBUTED BY (customer_id);
CREATE TABLE payments (...) DISTRIBUTED BY (customer_id);
```

## 5. Партиционирование

**Дистрибуция раскладывает данные ПО СЕГМЕНТАМ. Партиционирование делит данные
ВНУТРИ сегмента на части.** Это ортогональные механизмы, и путать их — самая
частая ошибка в теме.

```sql
CREATE TABLE events (...)
DISTRIBUTED BY (user_id)
PARTITION BY RANGE (event_date)
(START ('2025-01-01') END ('2026-01-01') EVERY (INTERVAL '1 month'));
```

Здесь `user_id` даёт равномерность и локальные соединения, а `event_date`
позволяет отсечь ненужные месяцы (**partition pruning**).

Зачем партиционирование:

- **Отсечение партиций** при фильтре по ключу партиционирования;
- **Мгновенное удаление старых данных**: `DROP PARTITION` вместо `DELETE` с
  многочасовой уборкой;
- **Точечная перезагрузка периода** подменой партиции — то же, что даёт
  идемпотентность в `airflow.idempotency`.

Чего делать не стоит: **слишком мелкие партиции**. Суточные партиции за пять
лет — это почти две тысячи объектов на таблицу, и планирование запроса
начинает стоить дороже выполнения. Ориентир — десятки или сотни партиций, а не
тысячи.

## 6. Ориентация хранения и сжатие

Greenplum позволяет выбирать способ хранения на уровне таблицы или партиции.

**Heap** — строковое хранение, как в PostgreSQL. Поддерживает `UPDATE` и
`DELETE` обычным способом. Для таблиц, которые часто меняются.

**Append-optimized, строковый** — оптимизирован для массовой вставки и чтения
целиком. Изменения дороги.

**Append-optimized, колоночный** — то же плюс колоночное хранение: читаются
только нужные колонки, сжатие лучше. Для больших таблиц фактов, из которых
берут несколько колонок из многих.

```sql
CREATE TABLE facts (...)
WITH (appendoptimized=true, orientation=column, compresstype=zstd, compresslevel=5)
DISTRIBUTED BY (id);
```

Правило выбора то же, что в `storage.formats`: колоночное для аналитического
чтения немногих колонок, строковое для доступа к записи целиком и для частых
изменений.

Полезная деталь: **разные партиции одной таблицы могут иметь разное
хранение**. Свежий месяц — heap, чтобы принимать правки; старые месяцы —
колоночные и сжатые. Это стандартный приём.

## 7. Эксплуатация

**`ANALYZE` обязателен.** Планировщик MPP принимает решения о типе Motion,
опираясь на статистику; ошибка в оценке размера приводит к Broadcast Motion
огромной таблицы. Ошибки статистики здесь дороже, чем в одиночном PostgreSQL.

**`VACUUM`** нужен по тем же причинам, что в PostgreSQL: MVCC оставляет
мёртвые строки.

**Загрузка данных.** Обычный `INSERT` идёт через координатор и упирается в
него. Для массовой загрузки существуют внешние таблицы и параллельная
загрузка, где данные идут сразу на сегменты, минуя координатор.

**Ресурсные группы** ограничивают потребление памяти и процессора разными
категориями пользователей — на общем хранилище это единственный способ не
дать одному аналитику положить систему.

## 8. Что ещё спросят

- **Почему запрос с `WHERE distribution_key = 'X'` медленный при большом
  объёме.** Потому что вся работа уходит на один сегмент: параллелизма нет.
- **Чем Greenplum отличается от ClickHouse.** Greenplum — MPP на базе
  PostgreSQL с полноценными транзакциями и соединениями; ClickHouse — движок,
  заточенный под быстрые агрегации, со слабыми соединениями и иной моделью
  изменений.
- **Что такое зеркала сегментов.** Реплики сегментов для отказоустойчивости:
  при потере сегмента его зеркало становится основным.
- **Почему нельзя обновлять колонку ключа дистрибуции.** Изменение значения
  означает переезд строки на другой сегмент; Greenplum такие обновления
  запрещает.
