# Spark: DataFrame, ленивость, план выполнения

> Конспект по документации Apache Spark: «RDD Programming Guide»,
> «Spark SQL Guide», «Performance Tuning».

Spark спрашивают на каждом собеседовании, где есть большие данные. Вопросы
почти всегда об одном: понимает ли человек, что код на драйвере и вычисление
на кластере — разные вещи.

## Что нужно уметь после этого узла

- Отличить трансформацию от действия и предсказать момент вычисления
- Назвать роли драйвера и исполнителей
- Прочитать план и найти в нём обмен данными
- Отличить узкую трансформацию от широкой
- Объяснить, когда `cache` помогает, а когда вредит
- Сказать, чем DataFrame выгоднее RDD и почему Python-UDF дорог

## 1. Драйвер и исполнители

**Драйвер** — процесс, где выполняется ваш код: строит план, дробит его на
задачи и раздаёт. **Исполнители** — процессы на узлах кластера, где реально
обрабатываются данные. Данные живут у исполнителей, распределённые по
**партициям**; партиция — единица параллелизма, одна задача обрабатывает одну
партицию.

Из этого следует всё остальное.

```python
df = spark.read.parquet("s3://data/events/")
rows = df.collect()  # ← все данные едут на драйвер
```

`collect()` стягивает **весь** набор в память драйвера. На датасете в сотню
гигабайт это гарантированный `OutOfMemoryError`, причём падает не кластер, а
драйвер — то есть падает всё приложение. Для просмотра есть `show(20)` и
`take(5)`, для выгрузки — запись в хранилище.

Та же ловушка мягче: `toPandas()`. Тот же сбор на драйвер, только с ещё одним
преобразованием.

## 2. Ленивость: трансформации и действия

**Трансформация** описывает, что сделать, и ничего не вычисляет:
`select`, `filter`, `withColumn`, `join`, `groupBy`. Результат — новый
DataFrame, то есть новый узел плана.

**Действие** запускает вычисление: `count`, `collect`, `show`, `write`,
`take`, `foreach`.

```python
df = spark.read.parquet(path)      # ничего не прочитано
df = df.filter(F.col("amount") > 0)  # ничего не посчитано
df = df.withColumn("day", F.to_date("created_at"))  # тоже ничего
df.write.parquet(out)              # ← вот здесь началась работа
```

Зачем это нужно: собрав весь план целиком, Spark оптимизирует его как единое
целое. Он протолкнёт фильтры к чтению (**predicate pushdown**), оставит только
нужные колонки (**projection pruning**), объединит подряд идущие операции в
одну стадию.

Практическое следствие, о котором спрашивают: **ошибка в трансформации
всплывёт не там, где написана**. Строка с `filter` отработает без единого
сообщения, а упадёт `write` десятью строками ниже — и в трассировке будет
именно он.

Второе следствие: **каждое действие пересчитывает всю цепочку заново**.

```python
df = spark.read.parquet(path).filter(...)  # дорогое чтение и фильтр
print(df.count())   # первый проход
print(df.count())   # ВТОРОЙ полный проход, всё считается снова
```

## 3. Узкие и широкие трансформации

**Узкая** трансформация: каждая выходная партиция зависит ровно от одной
входной. `filter`, `select`, `withColumn`, `map`. Выполняется на месте, без
передачи данных по сети.

**Широкая**: выходная партиция зависит от многих входных, поэтому данные надо
перераспределить между узлами. `groupBy`, `join`, `distinct`, `orderBy`,
`repartition`. Такое перераспределение и называется **shuffle**.

Shuffle — самая дорогая операция в Spark: запись промежуточных файлов на диск,
передача по сети, чтение на другой стороне. Оптимизация Spark в 90% случаев
сводится к тому, чтобы shuffle стало меньше или он стал дешевле (подробно —
в `spark.optimization`).

**Стадия (stage)** — участок плана между двумя shuffle. Границы стадий в
интерфейсе Spark ровно совпадают с местами обмена данными, поэтому число
стадий — быстрая оценка того, сколько раз данные перетасовывались.

## 4. План выполнения

```python
df.explain(True)
```

Показывает четыре плана: разобранный, проанализированный,
оптимизированный логический и **физический**. Смотреть в первую очередь надо
физический — именно он исполняется. Читается снизу вверх: нижние узлы
выполняются первыми.

Что искать:

- **`Exchange`** — это shuffle. Каждое такое слово в плане стоит денег.
- **`FileScan parquet` с `PushedFilters`** — фильтры дошли до чтения, значит
  лишние данные не читаются. Пустой список — повод разобраться.
- **`ReadSchema`** — какие колонки реально читаются. Если там все сорок, а
  нужно две, проекция не сработала.
- **Тип соединения**: `BroadcastHashJoin` (маленькая таблица разослана всем),
  `SortMergeJoin` (обе большие, обе перетасованы), `BroadcastNestedLoopJoin`
  (обычно признак беды — соединение без условия равенства).

**Adaptive Query Execution (AQE)** — механизм, меняющий план **по ходу
выполнения**, опираясь на фактические размеры данных. Он умеет схлопывать
лишние партиции после shuffle, переключать соединение на broadcast, когда
сторона оказалась маленькой, и разбивать перекошенные партиции. Из-за AQE план
в интерфейсе может отличаться от того, что показал `explain` до запуска, — это
не ошибка.

## 5. Партиции

Число партиций определяет параллелизм. Слишком мало — часть ядер простаивает и
партиция может не влезть в память. Слишком много — накладные расходы на задачу
превышают полезную работу.

Ориентир: партиция в **128–256 МБ**, число партиций кратно числу ядер
кластера.

- `repartition(n)` — перетасовать в n партиций. **Всегда shuffle**, зато
  распределение равномерное. Умеет и по колонке: `repartition("day")`.
- `coalesce(n)` — уменьшить число партиций **без shuffle**, склеивая
  соседние. Дешевле, но распределение может получиться неравномерным.

Типичное применение: `coalesce` перед записью, чтобы не породить тысячу
мелких файлов (см. `storage.formats`). Осторожно: `coalesce(1)` перед
записью сводит **всю** обработку к одному ядру, потому что уменьшение числа
партиций распространяется вверх по цепочке. Если нужен один файл после тяжёлых
вычислений, честнее `repartition(1)` — он поставит shuffle и сохранит
параллелизм до него.

## 6. cache и persist

`cache()` (то же, что `persist(MEMORY_AND_DISK)`) сохраняет результат, чтобы
следующее действие не пересчитывало цепочку.

```python
df = spark.read.parquet(path).filter(...).cache()
df.count()   # считает и кеширует
df.groupBy(...).count().show()  # берёт из кеша
```

Три вещи, которые надо помнить:

1. **`cache` ленив.** Он лишь помечает; данные окажутся в памяти после первого
   действия.
2. **Кеш занимает память исполнителей** — ту же, в которой идут вычисления.
   Закешированный ненужный датафрейм вытесняет полезные данные и делает работу
   медленнее. Отсюда `unpersist()`, когда датафрейм больше не нужен.
3. **Кешировать имеет смысл то, что читается несколько раз.** Датафрейм,
   используемый однократно, от `cache` только теряет.

Отдельный случай: кеш **не** заменяет запись промежуточного результата.
Длинная цепочка вычислений с кешем всё равно может быть пересчитана при потере
исполнителя — Spark восстановит данные по родословной. Если пересчёт стоит
дорого, надёжнее записать промежуток в хранилище.

## 7. DataFrame против RDD

**RDD** — низкоуровневый интерфейс: распределённая коллекция объектов, над
которой вы пишете произвольные функции. Spark их не понимает и не может
оптимизировать.

**DataFrame** — таблица со схемой. Операции описываются выражениями, которые
Spark разбирает: он знает, что `filter(col("a") > 5)` — это фильтр по колонке
`a`, и может протолкнуть его к чтению файла. Отсюда оптимизатор Catalyst и
генерация кода Tungsten.

Практический вывод: **писать надо на DataFrame/SQL**, а RDD оставить для
редких случаев, где нужен контроль, недоступный через выражения.

### Python-UDF

Питоновская функция, применённая к колонке, ломает эту схему:

```python
@F.udf("double")
def bad(x):
    return x * 1.1
```

Spark не понимает её содержимое — для него это чёрный ящик. Он не может ни
протолкнуть её вниз, ни сгенерировать код. Хуже того, данные приходится
**сериализовать из JVM в процесс Python и обратно** на каждую строку.

Порядок предпочтений:

1. Встроенная функция (`F.col("x") * 1.1`) — всегда, когда возможно.
2. Векторизованная pandas-UDF — сериализация идёт пакетами через Arrow, что
   в разы дешевле построчной.
3. Обычная Python-UDF — последнее средство.

## 8. Что ещё спросят

- **`spark.sql.shuffle.partitions`** — число партиций после shuffle, по
  умолчанию 200. На маленьких данных это 200 крошечных задач, на больших —
  слишком мало. С AQE подбирается автоматически.
- **Схема при чтении.** `inferSchema` для CSV — это лишний полный проход по
  файлу. Схему лучше задавать явно; у Parquet она уже внутри.
- **`count()` не бесплатен**: это действие с полным проходом. Ставить его в
  логи «чтобы посмотреть, сколько строк» на каждом шаге — распространённый
  способ удвоить время работы.
