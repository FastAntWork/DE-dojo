# Форматы хранения: Parquet, колоночность, объектные хранилища

> Конспект по документации Apache Parquet и Apache Iceberg, плюс то, что
> спрашивают на собеседованиях по этой теме.

Parquet упоминается в вакансиях почти всегда, когда есть Spark или озеро
данных. Спрашивают не «что такое Parquet», а почему он быстрый и в каких
случаях перестаёт им быть.

## Что нужно уметь после этого узла

- Объяснить выигрыш колоночного хранения и назвать случай, где его нет
- Назвать три механизма Parquet, экономящих чтение
- Выбрать колонку партиционирования и обосновать выбор
- Опознать проблему мелких файлов и назвать лечение
- Сказать, что добавляет Iceberg поверх Parquet

---

## 1. Строки против колонок

Строковое хранение (CSV, обычные таблицы OLTP) кладёт рядом **всю запись**:

```
[1, Иванов, 2025-01-01, 500] [2, Петров, 2025-01-02, 700] …
```

Колоночное кладёт рядом **одну колонку всех записей**:

```
[1, 2, 3, …] [Иванов, Петров, …] [2025-01-01, …] [500, 700, …]
```

Отсюда следуют оба главных свойства.

**Читается только нужное.** Запрос `SELECT sum(amount) FROM sales` в колоночном
формате трогает одну колонку из двадцати. В строковом придётся прочитать всё:
нужные байты размазаны по файлу. На широкой таблице это разница в разы, и
никакой индекс её не убирает.

**Сжимается лучше.** В одной колонке лежат однотипные и часто повторяющиеся
значения — дата, код региона, статус. Такое сжимается кратно сильнее, чем
чередование числа, строки и даты. Меньше байт на диске означает меньше
чтения, а на объектном хранилище — ещё и меньше денег за трафик.

**Где колоночность проигрывает.** Когда нужна вся запись целиком и по одной:
`SELECT * FROM sales WHERE id = 12345`. Тогда придётся собирать строку из
двадцати разных мест. Поэтому OLTP-базы остаются строковыми, а Parquet — это
формат аналитики, а не оперативной работы. Ответ «Parquet быстрее» без этой
оговорки на собеседовании считается неполным.

## 2. Как устроен Parquet

Файл делится на **row groups** (группы строк, обычно 128 МБ), внутри группы —
**column chunks** по одной на колонку, внутри чанка — **страницы**.

Такое устройство даёт три механизма экономии, и их стоит уметь назвать
раздельно.

**Проекция колонок.** Читаются только чанки нужных колонок. Остальные не
трогаются вовсе.

**Статистика.** Для каждой группы строк и каждой страницы хранятся `min`,
`max` и число `null`. Если запрос фильтрует `WHERE date = '2025-03-01'`, а у
группы `max(date) = '2025-02-28'`, вся группа пропускается не читая. Это
называется **predicate pushdown**: условие передаётся вниз, на уровень чтения
файла. Работает тем лучше, чем сильнее данные упорядочены по колонке фильтра —
на случайном порядке `min` и `max` почти у всех групп одинаковы, и пропустить
нечего. Отсюда практический приём: сортировать данные при записи по той
колонке, по которой будут фильтровать.

**Словарное кодирование.** Повторяющиеся значения заменяются на номера в
словаре. Колонка `region` из десяти значений на миллионе строк превращается в
миллион маленьких чисел плюс словарь. Поверх идёт RLE и общее сжатие (snappy,
zstd, gzip). Snappy — быстрее, zstd — плотнее; выбор зависит от того, что
дороже, процессор или хранилище.

**Схема лежит внутри файла.** Parquet самоописателен: типы колонок хранятся в
футере. Отсюда важное следствие — читатель не обязан знать схему заранее, но
и записать в тот же датасет файл с другой схемой значит получить ошибку при
чтении или тихую потерю колонки.

## 3. Партиционирование

Датасет обычно лежит не одним файлом, а деревом каталогов:

```
sales/dt=2025-03-01/part-0000.parquet
sales/dt=2025-03-02/part-0000.parquet
```

Значение партиции закодировано **в имени каталога**, а не в данных. Движок
читает пути, отбрасывает ненужные каталоги целиком и не открывает лежащие в
них файлы. Это **partition pruning** — самый дешёвый способ не читать данные,
потому что он работает ещё до открытия файла.

Правило выбора колонки: **низкая кардинальность и присутствие в фильтрах**.
Дата подходит почти всегда. `user_id` не подходит никогда — миллион каталогов
по одному файлу в каждом убивают и файловую систему, и планировщик, который
обязан перечислить их все.

Второе правило: партиция должна быть **достаточно крупной**. Ориентир —
сотни мегабайт. Если суточная партиция весит два мегабайта, партиционировать
надо по месяцу.

## 4. Проблема мелких файлов

Самая частая беда озера, и её любят спрашивать.

Симптом: запрос по небольшому объёму данных работает минуты, а в логах видно
десятки тысяч задач. Причина: датасет состоит из тысяч файлов по несколько
килобайт. Каждый файл — это отдельное сетевое обращение к хранилищу, чтение
футера, создание задачи. Накладные расходы превышают полезную работу в разы.

Откуда берётся: стриминг, пишущий микропакеты; ежечасная запись в суточную
партицию; `repartition` с большим числом частей; запись без коалесценции.

Лечение:

- **Компакция** — периодически переписывать мелкие файлы в крупные. Цель —
  файл размером порядка 128–512 МБ, то есть примерно одна группа строк.
- **Управлять числом частей при записи** — `coalesce`/`repartition` перед
  записью, чтобы не плодить по файлу на задачу.
- **Укрупнить партиции**, если дробность взялась оттуда.

## 5. Объектное хранилище — не файловая система

Parquet почти всегда лежит в S3 или совместимом хранилище (MinIO, Ceph, S3 у
облачного провайдера). Отличия, из которых вырастают ошибки:

- **Нет переименования.** `rename` — это копирование плюс удаление, то есть
  операция за деньги и время, а не мгновенная. Приёмы «записать во временный
  каталог и переименовать» из мира HDFS здесь работают плохо.
- **Нет каталогов.** Есть плоское пространство ключей, а «каталог» — префикс.
  Перечисление префикса с миллионом ключей стоит дорого.
- **Согласованность в конечном счёте** (у части провайдеров): только что
  записанный файл может не сразу появиться в листинге.
- **Оплата за запросы**, а не только за объём. Тысячи мелких файлов — это
  тысячи оплаченных GET.

## 6. Табличные форматы: Iceberg, Delta, Hudi

Parquet — формат **файла**. Он ничего не знает о том, что несколько файлов
вместе образуют таблицу. Отсюда проблемы, которые сам Parquet не решает:

- Нет атомарности: пока идёт запись, читатель видит половину данных.
- Нет `UPDATE` и `DELETE`: чтобы поправить одну строку, надо переписать файл.
- Нет истории: узнать, как таблица выглядела вчера, нельзя.
- Изменение схемы — ручная операция с риском развалить чтение.

Табличный формат добавляет над файлами **метаданные и журнал изменений**:
список файлов, входящих в текущую версию таблицы, статистику по ним и историю
снимков. Из этого получаются:

- **Атомарные коммиты** — читатель видит либо старую версию, либо новую.
- **Путешествие во времени** — чтение таблицы на момент в прошлом.
- **Эволюция схемы** — добавление и переименование колонок без переписывания.
- **Скрытое партиционирование** (Iceberg) — фильтр по `dt` работает, даже если
  физически партиции по месяцу: пользователю не нужно знать раскладку.
- **`MERGE INTO`** — то самое обновление строк, ради которого раньше городили
  полные перезаписи.

Формулировка, которую стоит запомнить для собеседования: **Parquet отвечает за
то, как лежат данные внутри файла, табличный формат — за то, какие файлы
составляют таблицу прямо сейчас.**

---

## 7. Что ещё спросят

- **Parquet против ORC.** Оба колоночные и похожи по идеям. Parquet
  распространён в экосистеме Spark и облаков, ORC — в мире Hive. Разница в
  деталях реализации, а не в подходе.
- **Avro.** Строковый формат со схемой, хорош для потоков и обмена
  сообщениями, где запись читают целиком. Не конкурент Parquet, а дополнение.
- **Почему не CSV.** Нет типов, нет схемы, нет статистики, нет сжатия по
  колонкам, нельзя прочитать часть. Годится как формат обмена, не как формат
  хранения.
