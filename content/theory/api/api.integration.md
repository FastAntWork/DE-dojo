# Интеграция с API: пагинация, ретраи, лимиты

> Практический узел. Забрать данные из чужого HTTP-сервиса — типовая задача
> инженера данных, и почти все грабли здесь одни и те же независимо от API.

Тема даёт много вопросов на собеседовании, потому что по ответам сразу видно,
писал ли человек выгрузку, которая работает каждую ночь, или только пробовал
запросы в блокноте.

## Что нужно уметь после этого узла

- Забрать все страницы и объяснить выбор способа пагинации
- Отличить повторяемую ошибку от неповторяемой
- Написать повтор с экспоненциальной задержкой и разбросом
- Соблюсти ограничение частоты и обработать 429
- Сделать выгрузку идемпотентной
- Сказать, где хранить ключ и что делать при утечке

---

## 1. Коды ответов, которые надо различать

| Код | Смысл | Повторять? |
|---|---|---|
| 200 | успех | — |
| 400 | плохой запрос | **нет**, повтор даст то же |
| 401 / 403 | не аутентифицирован / нет прав | **нет**, чинить доступ |
| 404 | не найдено | **нет** |
| 409 | конфликт состояния | зависит |
| 429 | слишком часто | **да**, с задержкой |
| 500 / 502 / 503 / 504 | сбой на той стороне | **да** |

Главное различение: **ошибки клиента (4xx) повторять бессмысленно**, кроме
429. **Ошибки сервера (5xx) и сетевые таймауты — повторять**, они часто
проходят сами.

Слепой повтор всего подряд — распространённая ошибка: выгрузка с неверным
ключом будет ломиться в API десять раз, получая 401, и в логах это выглядит
как проблема сети.

## 2. Пагинация

**По смещению** — `?limit=100&offset=500`. Просто и плохо:

- дорого на глубине: сервер обязан отобрать и отбросить 500 записей (та же
  беда, что у `OFFSET` в SQL);
- **данные разъезжаются**: если во время выгрузки добавилась запись, часть
  строк вернётся дважды, а часть будет пропущена.

**По курсору** — `?limit=100&cursor=eyJpZCI6NTAwfQ`. Сервер возвращает метку,
с которой продолжать. Устойчиво к вставкам и дёшево на любой глубине. Если API
даёт курсор — берите его.

**По ключу** — `?since_id=12345` или `?updated_after=2026-03-01T10:00:00Z`.
Частный случай курсора, который можно построить самому.

Универсальные правила выгрузки страниц:

```python
cursor = None
while True:
    page = fetch(cursor=cursor, limit=100)
    yield from page["items"]
    cursor = page.get("next_cursor")
    if not cursor or not page["items"]:
        break
```

- **Ограничивать число итераций.** Ошибка в условии выхода превращает выгрузку
  в бесконечный цикл, который заметят по счёту за трафик.
- **Сортировка обязана быть устойчивой.** Пагинация по неуникальному полю
  (только по дате) даёт пропуски при совпадающих значениях; сортировать нужно
  по паре «дата, идентификатор».

## 3. Повторы

```python
import random, time

def with_retries(call, attempts=5, base=1.0, cap=60.0):
    for attempt in range(attempts):
        try:
            response = call()
        except (TimeoutError, ConnectionError):
            pass
        else:
            if response.status_code < 500 and response.status_code != 429:
                return response

        if attempt == attempts - 1:
            raise

        delay = min(cap, base * 2 ** attempt)
        time.sleep(delay * (0.5 + random.random()))   # разброс
```

Что здесь важно:

**Экспоненциальная задержка.** Повторять раз в секунду упавший сервис —
значит мешать ему подняться. Задержка растёт: 1, 2, 4, 8 секунд.

**Случайный разброс (jitter).** Без него все клиенты, упавшие одновременно,
повторят запрос тоже одновременно и добьют сервис. Множитель со случайной
составляющей разводит их во времени.

**Потолок.** Без ограничения задержка вырастает до часов.

**Конечное число попыток.** Бесконечный повтор превращает задачу в вечно
висящую — и в оркестраторе она будет держать слот.

**Повторять можно только идемпотентные запросы.** `GET` — всегда. `POST`,
создающий заказ, — нет: повтор после таймаута может создать второй заказ,
потому что первый мог успешно выполниться, а ответ не дойти. Для таких
случаев API предоставляют ключ идемпотентности — уникальный идентификатор
операции, по которому сервер распознаёт повтор.

## 4. Ограничение частоты

Ответ **429 Too Many Requests** означает «слишком часто». Часто он приходит с
заголовком `Retry-After` — числом секунд или датой. **Его надо читать, а не
угадывать задержку**: сервер сообщает, когда можно.

Заголовки вида `X-RateLimit-Remaining` и `X-RateLimit-Reset` позволяют не
доводить до 429 вовсе — притормаживать заранее, когда остаток мал.

Простейший способ соблюдать лимит на своей стороне — выдерживать паузу между
запросами исходя из разрешённой частоты. Более аккуратный — алгоритм «дырявого
ведра» или «токенов», позволяющий короткие всплески.

И отдельное правило: **не распараллеливать выгрузку в двадцать потоков без
разрешения.** Это самый быстрый способ получить блокировку по адресу и
неприятный разговор с владельцем API.

## 5. Идемпотентность выгрузки

Всё, что сказано в узле про идемпотентность оркестрации, применимо и здесь.
Конкретно для API:

- **Границы периода брать из контекста прогона**, а не из текущего времени;
  иначе повторный запуск за вчера заберёт сегодняшние данные.
- **Записывать порцию атомарно**: подменой партиции или удалением и вставкой
  периода в одной транзакции.
- **Не полагаться на то, что API отдаст ровно то же самое.** Многие источники
  меняют записи задним числом; выгрузка по `updated_at` с окном перекрытия
  надёжнее, чем по `created_at`.
- **Сохранять сырой ответ.** Дешёвое и очень окупаемое решение: когда через
  неделю обнаружится ошибка в разборе, не придётся выкачивать всё заново — а
  источник может уже и не отдать те данные.

## 6. Практические детали клиента

**Таймауты обязательны.** Запрос без таймаута может висеть вечно, и задача
вместе с ним:

```python
requests.get(url, timeout=(5, 30))   # соединение, чтение
```

**Сессия вместо отдельных запросов.** Переиспользование соединения экономит
рукопожатие TLS на каждом запросе — на тысячах запросов это заметно.

**Потоковое чтение больших ответов.** `stream=True` и запись по частям, чтобы
не держать сто мегабайт JSON в памяти.

**Проверять статус явно.** `response.raise_for_status()` или ручная проверка:
`requests` не бросает исключение на 404 сам по себе, и без проверки вы
разберёте страницу ошибки как данные.

**Заголовок `User-Agent` с контактом.** Хороший тон и практическая польза:
когда выгрузка начнёт мешать, владелец API напишет, а не забанит молча.

## 7. Аутентификация и секреты

Способы, которые встречаются: ключ в заголовке, Basic-аутентификация, OAuth2 с
обновляемым токеном, подпись запроса.

Правила одинаковы для всех:

- **Ключ не в коде и не в git.** Переменная окружения, файл с правами 600 или
  хранилище секретов.
- **Ключ не в URL.** Параметры запроса попадают в логи прокси, в историю
  браузера и в метрики.
- **Ключ не в логах.** Логирование запроса целиком — самый частый способ
  утечки; заголовки надо маскировать.
- **При утечке — отозвать и заменить**, а не удалять коммит. Удаление из
  истории не отменяет того, что ключ уже видели.
- **Токен OAuth2 живёт недолго** и обновляется по refresh-токену. Обновление
  должно быть потокобезопасным, иначе параллельные задачи начнут обновлять его
  наперегонки и инвалидировать друг другу.

## 8. Что ещё спросят

- **Вебхуки против опроса.** Опрос проще и надёжнее в смысле контроля;
  вебхуки дают свежесть, но требуют доступного извне приёмника и обязаны быть
  идемпотентными — доставка повторяется.
- **Пагинация и параллелизм.** Курсорную пагинацию нельзя распараллелить по
  страницам: следующий курсор известен только после предыдущего запроса.
  Параллелить можно по независимым диапазонам, если API это позволяет.
- **Проверка полноты.** Если API отдаёт общее число записей, его стоит
  сверять с числом загруженных — дешёвая проверка, ловящая обрыв на середине.
- **Схема ответа меняется молча.** Это тот же контракт данных: разбор по
  явному списку полей ломается заметно, а `dict` целиком в базу — тихо.
