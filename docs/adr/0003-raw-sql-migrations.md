# ADR 0003. Миграции на чистом SQL со своим раннером, без alembic и ORM

- Статус: принято
- Дата: 2026-08-10

## Контекст

Стандартный выбор для Python-проекта с Postgres — SQLAlchemy плюс alembic.
Здесь он плохо согласуется с назначением проекта: SQL и устройство Postgres
являются предметом изучения. ORM прячет ровно то, что пользователь должен
научиться читать и писать, а `alembic revision --autogenerate` превращает
схему в производную от моделей, то есть в то, на что не смотрят.

При этом сами по себе гарантии alembic нужны: порядок применения, учёт
применённого, атомарность.

## Решение

Миграции — файлы `migrations/versions/NNN_snake_case.sql` на чистом SQL.
Применяет их `dojo.core.migrate` (~150 строк). Запросы в приложении пишутся
через asyncpg вручную, без ORM.

Раннер даёт четыре гарантии, каждая закрыта тестом:

1. **Порядок** по числовому префиксу, а не лексикографический — иначе `010`
   применилось бы раньше `9`.
2. **Атомарность**: каждая миграция в своей транзакции. Файл, который нельзя
   выполнить в транзакции (`CREATE INDEX CONCURRENTLY`), помечается строкой
   `-- dojo:no-transaction`.
3. **Неизменность применённого**: хранится контрольная сумма, правка задним
   числом роняет запуск вместо тихого расхождения схемы с историей.
4. **Отсутствие дыр**: миграция с номером ниже максимального применённого —
   ошибка, так ловится ветка, отставшая от main.

Плюс advisory-lock против одновременного `make up` и CI.

Контрольная сумма считается по нормализованному тексту (обрезанные хвостовые
пробелы, один перевод строки в конце). Иначе хук `trailing-whitespace`,
прошедший по репозиторию, сломал бы сверку для миграций месячной давности.

## Последствия

Схема пишется руками и читается как учебный материал: `001_init.sql` содержит
комментарии о том, почему сделано именно так.

Autogenerate отсутствует. Забыть миграцию к изменению кода технически можно —
защищает только интеграционный тест, поднимающий чистую БД.

Правка применённой миграции невозможна: нужна новая. Это уже сработало —
колонку `deprecated_at` в `tasks` пришлось добавлять миграцией 002 вместо
правки 001, ровно как и задумано.

Проект не тянет SQLAlchemy, что заметно на времени сборки образа и на объёме
зависимостей, которые пользователь будет читать.
